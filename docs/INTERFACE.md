# 인터페이스 명세서 — 클라이언트 → Coordinator REST API

클라이언트 프로그램이 coordinator 를 호출해 이관 작업을 맡기고 결과를 확인하는 데 필요한
엔드포인트만 모은 명세서다. 주고받는 JSON 을 필드 하나가 한 줄이 되도록 펼쳐서, 이 문서의 표를
엑셀로 그대로 옮길 수 있게 했다.

executor 를 직접 부르는 내부 엔드포인트와 대시보드용 조회 엔드포인트는 여기에 담지 않았다.
클라이언트는 coordinator 한 곳만 알면 되고, 나머지는 coordinator 가 대신 처리한다. 전체 엔드포인트
목록과 모니터링 계열은 `artifacts/interface.md` 에 있다.

같은 내용을 엑셀로도 두었다. `INTERFACE.xlsx` 는 엔드포인트마다 시트를 하나씩 두고 여기와 같은 열을
담으며, 맨 앞 개요 시트에서 전체 목록과 입력·출력 항목 수를 볼 수 있다. 검토 의견을 직접 달거나 사내
표준 양식에 옮겨 붙일 때 쓴다. **내용을 고쳤다면 이 문서와 엑셀을 함께 갱신한다.**

## 표를 읽는 법

표는 엔드포인트마다 하나씩 두었고, 열 구성은 다음과 같다.

| 열 | 뜻 |
|---|---|
| `NO` | 그 표 안에서 필드가 놓인 순서 |
| `필드명(한글)` | 필드의 뜻을 우리말로 옮긴 이름 |
| `필드명(영문)` | 실제 JSON 에 쓰이는 이름. 프로그램이 참조하는 이름이다 |
| `부모필드명` | 이 필드를 담고 있는 바로 위 노드의 영문명. 최상위 필드는 `-` 다 |
| `데이터 타입` | 값의 종류 |
| `길이` | 값이 얼마나 길 수 있는지 |
| `반복 건수` | 배열일 때 원소가 몇 개까지 오는지. 배열이 아니면 `-` 다 |
| `입출력 구분` | 보내는 것은 `I`, 받는 것은 `O` |
| `설명` | 무엇을 담는 자리인지와 지켜야 할 규칙 |

**계층은 `부모필드명` 으로 표현한다.** `tasks` 배열 안의 `task_id` 는 부모필드명이 `tasks` 이고,
그 안의 `phases` 배열에 있는 `name` 은 부모필드명이 `phases` 다. 3단계 이상이어도 **바로 위 부모
하나만** 적으며, 배열 자체도 한 줄을 차지하므로 그 줄을 따라가면 전체 경로를 복원할 수 있다.

**데이터 타입**은 JSON 의 여섯 가지에 `enum` 을 더한 것이다. `string`·`integer`·`number`·
`boolean`·`object`·`array` 에 더해, 미리 정해 둔 값 중에서만 골라야 하는 자리를 `enum` 으로 적었다.

**길이**는 타입에 따라 읽는 법이 다르다. 글자는 최대 몇 자인지를 적고 상한이 없으면 `가변` 이다.
숫자는 길이 대신 허용 범위를 적고 범위가 없으면 `-` 다. 참·거짓과 객체, 배열은 모두 `-` 다.

**반복 건수**의 `N` 은 상한이 정해져 있지 않다는 뜻이다. 예를 들어 파티션 값 개수는 보낸 SQL 의
`IN` 목록 길이에 따라 달라지므로 `1~N` 으로 적었다.

**입력에는 본문 필드만이 아니라 헤더와 경로·질의 파라미터도 함께 담았다.** 클라이언트가 준비해야
하는 것이 모두 한 표에 모이는 편이 낫기 때문이며, 어디에 실어 보내는지는 설명에 적었다.

**비어 있어도 되는 필드**는 설명 첫머리에 `[선택]` 이라고 적었다. 표시가 없으면 반드시 채워야 하는
값이고, 출력 쪽의 `[선택]` 은 상황에 따라 `null` 로 올 수 있다는 뜻이다.

## 공통 규약

coordinator 는 기본적으로 `8088` 포트에서 듣는다. 이 문서의 모든 URI 앞에는
`http://<coordinator 주소>:8088` 이 붙는다. 주고받는 내용은 모두 JSON 이고 글자는 UTF-8 이며, 본문을
보내는 요청에는 `Content-Type: application/json` 을 붙인다. 사내망 전용이라 별도의 인증 절차는 없다.

시각 필드는 이름이 `_at` 으로 끝나고 값은 `yyyy-MM-dd HH:mm:ss.sss` 모양의 23자 글자다. **시간대
표시가 없는 한국 시각**이므로 따로 변환하지 않는다. 작업 식별자는 `job_` 에 12자리가 붙은 16자이고
태스크 식별자는 `t_` 에 12자리가 붙은 14자이며, 둘 다 서버가 만들어 준다.

응답 코드는 다음과 같다.

| 코드 | 언제 나오나 |
|---|---|
| `200` | 조회가 성공했을 때. 모의 실행이거나 같은 멱등 키로 기존 작업을 재생할 때도 이 코드다 |
| `202` | 작업을 접수했을 때. 실행은 아직 시작되지 않았다 |
| `400` | 템플릿 기능이 꺼져 있거나 접속 정보가 없어 처리할 수 없을 때 |
| `404` | 찾는 작업·태스크·템플릿이 없을 때 |
| `409` | 이미 끝난 작업을 취소하려 했거나, 재실행할 대상이 없거나, 같은 멱등 키에 다른 본문이 왔을 때 |
| `422` | 보낸 내용이 규칙에 맞지 않을 때 |
| `429` | 동시에 처리할 수 있는 작업 수를 넘겼을 때. `Retry-After` 헤더가 함께 온다 |
| `502` | coordinator 가 executor 나 데이터베이스에 닿지 못했을 때 |

실패 응답의 본문은 두 가지다. `422` 만 프로그램이 사유를 갈라 볼 수 있도록 코드를 함께 준다.

| NO | 필드명(한글) | 필드명(영문) | 부모필드명 | 데이터 타입 | 길이 | 반복 건수 | 입출력 구분 | 설명 |
|---|---|---|---|---|---|---|---|---|
| 1 | 오류 코드 | `error_code` | - | string | 최대 40 | - | O | `422` 응답에만 있다. 실패 사유를 나타내는 고정 코드다 |
| 2 | 오류 메시지 | `message` | - | string | 가변 | - | O | `422` 응답에만 있다. 무엇을 고쳐야 하는지 설명한다 |
| 3 | 오류 상세 | `detail` | - | string | 가변 | - | O | `400`·`404`·`409`·`429`·`502` 응답의 사람이 읽을 설명이다 |

주요 `error_code` 는 `NOT_A_SELECT`·`MULTIPLE_STATEMENTS`·`PARSE_ERROR`(보낸 SQL 자체의 문제),
`MISSING_PARTITION_COLUMN`·`NO_PARTITION_IN_CLAUSE`·`EMPTY_IN_LIST`·`NEGATED_IN`·
`SUBQUERY_IN_CLAUSE`(분할 기준의 문제), `MISSING_REQUIRED_FIELDS`·`STAGE_INSERT_REQUIRES_FIELDS`
(필수 필드 누락), `TEMPLATE_NOT_FOUND`·`TEMPLATE_PARAM_ERROR`·`TEMPLATE_MISSING_SIGN_VAR`(템플릿
문제), `TASK_RANGE_EMPTY`·`TASK_RANGE_TOO_LARGE`(날짜 분할 구간 문제)다.

## 엔드포인트 목록

클라이언트가 쓰는 순서로 여덟 개다. `IF-C-001` 로 작업을 맡기고 `IF-C-002` 로 진행률을 지켜보다가
끝나면 `IF-C-004` 로 건수를 확인하는 것이 기본 흐름이고, 일부가 실패했다면 `IF-C-006` 으로 실패한
몫만 다시 돌린다.

| NO | 인터페이스 ID | 인터페이스명 | 메서드 | URI | 방식 |
|---|---|---|---|---|---|
| 1 | `IF-C-001` | 이관 작업 생성 | POST | `/jobs` | 비동기 |
| 2 | `IF-C-002` | 작업 진행률 조회 | GET | `/jobs/{job_id}/status` | 동기 |
| 3 | `IF-C-003` | 작업 상세 조회 | GET | `/jobs/{job_id}` | 동기 |
| 4 | `IF-C-004` | 작업 결과 조회 | GET | `/jobs/{job_id}/result` | 동기 |
| 5 | `IF-C-005` | 작업 취소 | POST | `/jobs/{job_id}/cancel` | 동기 |
| 6 | `IF-C-006` | 실패 파티션 재실행 | POST | `/jobs/{job_id}/retry` | 비동기 |
| 7 | `IF-C-007` | 템플릿 쿼리 실행 | POST | `/query-execute` | 동기 |
| 8 | `IF-C-008` | 템플릿 목록 조회 | GET | `/templates` | 동기 |

## IF-C-001 이관 작업 생성

| 항목 | 내용 |
|---|---|
| 인터페이스 ID | `IF-C-001` |
| 메서드 · URI | `POST /jobs` |
| 방식 | 비동기. 접수만 확정하고 `202` 로 작업 번호를 돌려준다 |
| 설명 | 옮길 SELECT 를 검증·분할해 executor 들에게 나눠 준다 |

보내는 방법이 둘이다. SQL 전문을 그대로 보내거나, 서버에 등록된 템플릿 이름과 값만 보낸다.
`template_id` 를 채우면 템플릿 방식이고 이때 `sql` 은 비워도 된다. 실제 이관은 응답을 준 뒤에
진행되므로 진행률은 `IF-C-002` 로 따로 확인한다.

같은 요청을 두 번 보내도 안전하게 하려면 `Idempotency-Key` 헤더를 쓴다. 같은 키에 같은 본문이면
기존 작업을 `200` 과 `Idempotency-Replayed: true` 헤더로 재생하고, 본문이 다르면 `409` 로 거절한다.

골라 대신 물어보고, Greenplum 과 이력 데이터베이스는 coordinator 가 직접 실행한다.

## 호출 순서

정리하면 클라이언트는 다음 순서로 부른다. 템플릿을 쓴다면 `IF-C-008` 로 파라미터를 확인하고,
`IF-C-001` 로 작업을 맡겨 `job_id` 를 받는다. 그다음 `IF-C-002` 를 몇 초 간격으로 부르며 `status`
가 종료 상태가 되기를 기다리고, 끝나면 `IF-C-004` 로 적재 건수를 확인한다.

`status` 가 `PARTIAL` 이나 `FAILED` 면 `IF-C-003` 으로 어느 조각이 왜 실패했는지 확인한 뒤
`IF-C-006` 으로 실패분만 다시 돌린다. 이때 새 `job_id` 가 나오므로 그 번호로 다시 폴링한다. 도중에
멈춰야 하면 `IF-C-005` 를 부른다.

폴링 간격은 5초 안팎이 무난하다. `IF-C-002` 는 가볍지만 조각이 많은 작업을 `IF-C-003` 으로 자주
부르면 응답이 커지므로, 상세 조회는 상태가 바뀌었을 때만 한 번씩 부르는 편이 낫다.
