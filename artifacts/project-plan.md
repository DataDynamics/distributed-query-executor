# 프로젝트 관리 계획서

이 문서는 **분석 Application 의 백엔드를 Greenplum DB 에서 WarehousePG 로 전환하는 프로젝트**를
어떻게 끌고 갈 것인지 적어 둔 것이다. 무엇을 왜 하는지, 누가 언제까지 무엇을 만들어 내는지, 그리고
그 과정에서 무엇을 관리할 것인지를 담는다.

작성하면서 계속 채워 나가는 문서다. 지금 비어 있는 절은 정해지는 대로 이 문서에 더한다.

---

## 1. 프로젝트 관리

### 1.1 개요

**한 문장으로 말하면, 분석 Application 이 바라보는 데이터베이스를 바꾸는 프로젝트다.** 지금은 분석
Application 이 Greenplum DB 를 백엔드로 두고 동작한다. 이 프로젝트가 끝나면 같은 Application 이
WarehousePG 를 백엔드로 두고 동작한다.

바꾸는 일은 두 갈래로 나뉜다.

**첫째는 데이터를 옮기는 일이다.** 분석에 쓸 데이터를 Impala 에서 추출해 WarehousePG 에 적재한다.
Application 이 WarehousePG 를 바라보게 하려면 그 안에 데이터가 먼저 들어가 있어야 하므로, 이 갈래가
앞선다. 옮기는 양이 크고 주기적으로 되풀이되므로 한 번 옮기고 끝나는 일이 아니라 **되풀이할 수 있는
이관 체계를 갖추는 일**로 본다.

**둘째는 Application 을 전환하는 일이다.** 분석 Application 이 접속하는 대상과 실행하는 쿼리를
Greenplum DB 기준에서 WarehousePG 기준으로 바꾼다. 화면과 기능은 그대로 두되 그 아래에서 데이터를
읽어 오는 곳만 갈아 끼우는 것이 목표다. 사용자가 보기에 달라지는 것이 없어야 전환이 성공한 것이다.

**전환 전과 후는 이렇게 달라진다.**

| 구분 | 전환 전 | 전환 후 |
|---|---|---|
| 분석 Application 의 백엔드 | Greenplum DB | WarehousePG |
| 분석 데이터의 출처 | Greenplum DB 에 이미 있던 데이터 | Impala 에서 추출해 적재한 데이터 |
| 데이터가 들어오는 방법 | (기존 적재 경로) | Impala → 추출·적재 → WarehousePG |
| 사용자가 보는 화면 | 그대로 | 그대로 |

**이 프로젝트의 성패를 가르는 것은 "같은 결과가 나오는가"다.** 백엔드를 바꾸었을 때 같은 조건으로
조회한 결과가 전환 전과 같아야 한다. 그래서 데이터를 옮기는 일과 Application 을 바꾸는 일 못지않게,
양쪽 결과를 맞춰 보는 검증이 중요한 몫을 차지한다.

**아직 정해지지 않은 것들**은 이 문서의 뒤 절에서 다룬다. 수행 기간과 단계별 일정, 참여 조직과 역할,
산출물 목록, 위험 요소와 대응 방안, 품질과 형상 관리 기준이 여기에 해당한다.

### 1.2 목적과 범위

#### 목적

**이 프로젝트의 목적은 분석 Application 이 WarehousePG 위에서 지금과 다름없이 동작하게 만드는
것이다.** 데이터베이스를 바꾸는 일 자체가 목적이 아니라, 바꾸고 나서도 쓰는 사람이 달라진 것을
느끼지 못하게 하는 것이 목적이다. 그래서 "무엇을 새로 만들었나"보다 "무엇이 그대로인가"로 성패를
가른다.

여기에 하나가 더 붙는다. **데이터를 옮기는 일이 한 번으로 끝나지 않는다는 점**이다. 분석 데이터는
계속 쌓이므로 Impala 에서 WarehousePG 로 옮기는 일도 계속 되풀이된다. 그래서 이번에 옮기고 마는
것이 아니라, 다음에도 같은 방법으로 옮길 수 있는 **체계**를 남기는 것까지가 목적에 들어간다.

목적을 네 가지로 나누고 각각 무엇으로 달성을 판정할지 함께 정리하면 다음과 같다.

| NO | 목적 | 무엇으로 달성을 판정하는가 |
|---|---|---|
| 1 | 분석 Application 의 백엔드를 WarehousePG 로 전환한다 | 모든 화면과 기능이 WarehousePG 만 바라보고 정상 동작한다 |
| 2 | 전환 전후의 분석 결과가 같음을 보인다 | 같은 조건으로 조회한 결과가 건수와 값 모두 일치한다 |
| 3 | 되풀이할 수 있는 이관 체계를 갖춘다 | 정해진 주기에 사람 손 없이 이관이 돌고 실패를 알아챌 수 있다 |
| 4 | 사용자가 겪는 불편을 최소화한다 | 전환에 필요한 중단 시간이 합의된 범위 안에 든다 |

**2번이 가장 중요하다.** 화면이 뜨고 쿼리가 도는 것만으로는 전환에 성공했다고 할 수 없다. 숫자가
전과 다르면 그 순간부터 분석 결과를 믿을 수 없게 되고, 되돌리는 비용도 그만큼 커진다.

#### 범위

이 프로젝트가 **하는 일**은 다섯 갈래다.

| NO | 구분 | 하는 일 |
|---|---|---|
| 1 | 대상 선정 | 분석 Application 이 실제로 쓰는 테이블과 항목을 추려 이관 대상을 확정한다 |
| 2 | WarehousePG 준비 | 대상 테이블의 스키마를 만들고 분산 방식과 권한을 정한다 |
| 3 | 데이터 이관 | Impala 에서 추출해 WarehousePG 에 적재하고, 주기 실행과 실패 처리를 갖춘다 |
| 4 | Application 전환 | 접속 정보와 쿼리를 WarehousePG 기준으로 바꾸고 동작을 확인한다 |
| 5 | 검증과 전환 | 전후 결과를 대사하고, 합의된 시점에 전환한 뒤 안정화한다 |

**하지 않는 일**도 분명히 해 둔다. 범위를 넓게 잡으면 정작 전환이 늦어지기 때문이다.

| NO | 하지 않는 일 | 왜 빼는가 |
|---|---|---|
| 1 | 분석 Application 의 기능 추가와 화면 변경 | 전환과 기능 변경을 함께 하면 문제가 생겼을 때 원인을 가릴 수 없다 |
| 2 | 원천 시스템(Impala) 자체의 변경 | 읽어 오기만 하며 원천의 구조나 적재 방식은 건드리지 않는다 |
| 3 | 새로운 분석 지표나 리포트 개발 | 전환이 끝난 뒤 별도 과제로 다룬다 |
| 4 | Greenplum DB 의 폐기와 자원 회수 | 되돌릴 길을 남겨 두어야 하므로 안정화가 끝난 뒤 따로 정한다 |

**전제 두 가지**를 두고 계획을 세웠다. 하나는 분석 Application 의 화면과 기능이 이번 프로젝트 동안
바뀌지 않는다는 것이고, 다른 하나는 이관에 필요한 데이터가 Impala 에 이미 갖춰져 있다는 것이다. 둘
중 하나라도 어긋나면 범위와 일정을 다시 잡아야 한다.

**아직 확정하지 못한 것**은 이관 대상 테이블의 목록과 규모, 이관 주기, 그리고 전환에 쓸 수 있는
중단 시간이다. 이 셋이 정해져야 일정과 투입 규모를 계산할 수 있으므로 착수 직후에 먼저 확정한다.
