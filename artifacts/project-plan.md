# 프로젝트 관리 계획서

이 문서는 **분석 Application 의 백엔드를 Greenplum DB 에서 WarehousePG 로 전환하는 프로젝트**를
어떻게 끌고 갈 것인지 적어 둔 것이다. 무엇을 왜 하는지, 누가 언제까지 무엇을 만들어 내는지, 그리고
그 과정에서 무엇을 관리할 것인지를 담는다.

작성하면서 계속 채워 나가는 문서다. 지금 비어 있는 절은 정해지는 대로 이 문서에 더한다.

---

## 1. 프로젝트 관리

### 1.1 개요

**한 문장으로 말하면, 분석 Application 이 바라보는 데이터베이스를 바꾸는 프로젝트다.** 지금은 분석
Application 이 Greenplum DB 를 백엔드로 두고 동작한다. 이 프로젝트가 끝나면 같은 Application 이
WarehousePG 를 백엔드로 두고 동작한다.

바꾸는 일은 두 갈래로 나뉜다.

**첫째는 데이터를 옮기는 일이다.** 분석에 쓸 데이터를 Impala 에서 추출해 WarehousePG 에 적재한다.
Application 이 WarehousePG 를 바라보게 하려면 그 안에 데이터가 먼저 들어가 있어야 하므로, 이 갈래가
앞선다. 옮기는 양이 크고 주기적으로 되풀이되므로 한 번 옮기고 끝나는 일이 아니라 **되풀이할 수 있는
이관 체계를 갖추는 일**로 본다.

**둘째는 Application 을 전환하는 일이다.** 분석 Application 이 접속하는 대상과 실행하는 쿼리를
Greenplum DB 기준에서 WarehousePG 기준으로 바꾼다. 화면과 기능은 그대로 두되 그 아래에서 데이터를
읽어 오는 곳만 갈아 끼우는 것이 목표다. 사용자가 보기에 달라지는 것이 없어야 전환이 성공한 것이다.

**전환 전과 후는 이렇게 달라진다.**

| 구분 | 전환 전 | 전환 후 |
|---|---|---|
| 분석 Application 의 백엔드 | Greenplum DB | WarehousePG |
| 분석 데이터의 출처 | Greenplum DB 에 이미 있던 데이터 | Impala 에서 추출해 적재한 데이터 |
| 데이터가 들어오는 방법 | (기존 적재 경로) | Impala → 추출·적재 → WarehousePG |
| 사용자가 보는 화면 | 그대로 | 그대로 |

**이 프로젝트의 성패를 가르는 것은 "같은 결과가 나오는가"다.** 백엔드를 바꾸었을 때 같은 조건으로
조회한 결과가 전환 전과 같아야 한다. 그래서 데이터를 옮기는 일과 Application 을 바꾸는 일 못지않게,
양쪽 결과를 맞춰 보는 검증이 중요한 몫을 차지한다.

**아직 정해지지 않은 것들**은 이 문서의 뒤 절에서 다룬다. 수행 기간과 단계별 일정, 참여 조직과 역할,
산출물 목록, 위험 요소와 대응 방안, 품질과 형상 관리 기준이 여기에 해당한다.

### 1.2 목적과 범위

#### 목적

**이 프로젝트의 목적은 분석 Application 이 WarehousePG 위에서 지금과 다름없이 동작하게 만드는
것이다.** 데이터베이스를 바꾸는 일 자체가 목적이 아니라, 바꾸고 나서도 쓰는 사람이 달라진 것을
느끼지 못하게 하는 것이 목적이다. 그래서 "무엇을 새로 만들었나"보다 "무엇이 그대로인가"로 성패를
가른다.

여기에 하나가 더 붙는다. **데이터를 옮기는 일이 한 번으로 끝나지 않는다는 점**이다. 분석 데이터는
계속 쌓이므로 Impala 에서 WarehousePG 로 옮기는 일도 계속 되풀이된다. 그래서 이번에 옮기고 마는
것이 아니라, 다음에도 같은 방법으로 옮길 수 있는 **체계**를 남기는 것까지가 목적에 들어간다.

목적을 네 가지로 나누고 각각 무엇으로 달성을 판정할지 함께 정리하면 다음과 같다.

| NO | 목적 | 무엇으로 달성을 판정하는가 |
|---|---|---|
| 1 | 분석 Application 의 백엔드를 WarehousePG 로 전환한다 | 모든 화면과 기능이 WarehousePG 만 바라보고 정상 동작한다 |
| 2 | 전환 전후의 분석 결과가 같음을 보인다 | 같은 조건으로 조회한 결과가 건수와 값 모두 일치한다 |
| 3 | 되풀이할 수 있는 이관 체계를 갖춘다 | 정해진 주기에 사람 손 없이 이관이 돌고 실패를 알아챌 수 있다 |
| 4 | 사용자가 겪는 불편을 최소화한다 | 전환에 필요한 중단 시간이 합의된 범위 안에 든다 |

**2번이 가장 중요하다.** 화면이 뜨고 쿼리가 도는 것만으로는 전환에 성공했다고 할 수 없다. 숫자가
전과 다르면 그 순간부터 분석 결과를 믿을 수 없게 되고, 되돌리는 비용도 그만큼 커진다.

#### 범위

이 프로젝트가 **하는 일**은 다섯 갈래다.

| NO | 구분 | 하는 일 |
|---|---|---|
| 1 | 대상 선정 | 분석 Application 이 실제로 쓰는 테이블과 항목을 추려 이관 대상을 확정한다 |
| 2 | WarehousePG 준비 | 대상 테이블의 스키마를 만들고 분산 방식과 권한을 정한다 |
| 3 | 데이터 이관 | Impala 에서 추출해 WarehousePG 에 적재하고, 주기 실행과 실패 처리를 갖춘다 |
| 4 | Application 전환 | 접속 정보와 쿼리를 WarehousePG 기준으로 바꾸고 동작을 확인한다 |
| 5 | 검증과 전환 | 전후 결과를 대사하고, 합의된 시점에 전환한 뒤 안정화한다 |

**하지 않는 일**도 분명히 해 둔다. 범위를 넓게 잡으면 정작 전환이 늦어지기 때문이다.

| NO | 하지 않는 일 | 왜 빼는가 |
|---|---|---|
| 1 | 분석 Application 의 기능 추가와 화면 변경 | 전환과 기능 변경을 함께 하면 문제가 생겼을 때 원인을 가릴 수 없다 |
| 2 | 원천 시스템(Impala) 자체의 변경 | 읽어 오기만 하며 원천의 구조나 적재 방식은 건드리지 않는다 |
| 3 | 새로운 분석 지표나 리포트 개발 | 전환이 끝난 뒤 별도 과제로 다룬다 |
| 4 | Greenplum DB 의 폐기와 자원 회수 | 되돌릴 길을 남겨 두어야 하므로 안정화가 끝난 뒤 따로 정한다 |

**전제 두 가지**를 두고 계획을 세웠다. 하나는 분석 Application 의 화면과 기능이 이번 프로젝트 동안
바뀌지 않는다는 것이고, 다른 하나는 이관에 필요한 데이터가 Impala 에 이미 갖춰져 있다는 것이다. 둘
중 하나라도 어긋나면 범위와 일정을 다시 잡아야 한다.

**아직 확정하지 못한 것**은 이관 대상 테이블의 목록과 규모, 이관 주기, 그리고 전환에 쓸 수 있는
중단 시간이다. 이 셋이 정해져야 일정과 투입 규모를 계산할 수 있으므로 착수 직후에 먼저 확정한다.

## 2. 진척 관리

### 2.1 개요

**이 프로젝트의 모든 일정은 JIRA 한 곳에서 관리한다.** 확정된 요구사항을 JIRA 에 이슈로 등록하고,
그 요구사항을 실제로 해내기 위해 필요한 일을 Task 로 쪼개어 요구사항 아래에 등록한다. 계획도 실적도
JIRA 에 남기므로, 지금 어디까지 왔는지 알고 싶을 때 다른 자료를 뒤질 필요가 없다.

**요구사항과 Task 를 두 층으로 나누는 데는 이유가 있다.** 요구사항은 "무엇을 해 달라"는 약속이고
Task 는 "그것을 하려면 무엇을 해야 하는가"이다. 층을 나누어 두면 요구사항 단위로는 발주 측이 진척을
읽고, Task 단위로는 수행 측이 일을 나눠 맡을 수 있다. 요구사항 하나가 끝났는지는 그 아래 Task 가
모두 끝났는지로 판정하므로, 진척률이 사람의 느낌이 아니라 계산으로 나온다.

**계획 대비 실적으로 진척을 본다.** Task 마다 담당자와 시작·종료 예정일을 넣어 일정 기준선을 만들고,
담당자가 상태와 진척을 갱신하면 그 합이 곧 프로젝트 진척이 된다. 계획보다 늦어진 Task 는 주간
점검에서 걸러 내어 원인과 조치를 이슈로 남긴다.

**JIRA 밖에서 따로 관리하는 일정표는 두지 않는다.** 같은 일정을 두 곳에 적으면 반드시 어긋나고,
어느 쪽이 맞는지 다투는 데 시간이 든다. 보고용 자료가 필요하면 JIRA 에서 뽑아 만든다.

### 2.2 진척 관리

진척 관리는 여덟 단계로 돌아간다. 1~3번은 시작할 때 한 번 하고, 4~7번은 프로젝트가 끝날 때까지
되풀이하며, 8번은 요구사항이 끝날 때마다 한다.

각 절차가 무엇을 받아 무엇을 남기는지는 다음과 같다. `수행 내용` 열은 절차 이름만으로는 무엇을
하는지 알기 어려워 덧붙인 것이다.

| NO | 수행 절차 | 수행 내용 | 입력물 | 산출물 |
|---|---|---|---|---|
| 1 | 요구사항 등록 | 확정된 요구사항을 JIRA 이슈로 등록하고 우선순위와 담당을 지정한다 | 요구사항 정의서, 범위 합의 내용 | JIRA 요구사항 이슈, 요구사항 목록 |
| 2 | Task 분해와 등록 | 요구사항마다 필요한 일을 Task 로 쪼개어 하위 이슈로 등록한다 | JIRA 요구사항 이슈, 작업 분류 체계(WBS) | JIRA Task 이슈, 요구사항–Task 연결 |
| 3 | 일정 기준선 수립 | Task 에 담당자와 시작·종료 예정일을 넣어 기준 일정을 확정한다 | JIRA Task 이슈, 투입 인력 계획 | 일정 기준선, 마일스톤 목록 |
| 4 | 일일 진척 갱신 | 담당자가 맡은 Task 의 상태와 진척을 매일 갱신한다 | JIRA Task 이슈, 당일 작업 결과 | 갱신된 Task 상태, 잔여 공수 |
| 5 | 주간 진척 점검 | 계획 대비 실적을 집계하고 지연 Task 를 가려내 회의에 올린다 | 갱신된 Task 상태, 일정 기준선 | 주간 진척 보고서, 지연 Task 목록 |
| 6 | 이슈·위험 처리 | 지연과 장애를 이슈로 등록해 조치·담당·기한을 정하고 끝까지 좇는다 | 지연 Task 목록, 현장에서 나온 문제 | JIRA 이슈, 조치 결과 기록 |
| 7 | 변경 관리 | 요구사항이 바뀌면 영향을 따져 승인받고 기준선을 다시 잡는다 | 변경 요청, 영향 분석 결과 | 변경 승인 기록, 갱신된 일정 기준선 |
| 8 | 요구사항 완료 확인 | 하위 Task 가 모두 끝났는지 확인하고 요구사항을 종료 처리한다 | 완료된 Task, 검증 결과 | 완료 확인 기록, 종료된 요구사항 이슈 |

**진척률은 Task 를 세어 구한다.** 요구사항의 진척은 그 아래 Task 중 끝난 것의 비율이고, 프로젝트
전체의 진척은 요구사항의 진척을 규모로 가중해 더한 값이다. 사람마다 다르게 매기는 체감 진척을
쓰지 않는 이유는, 그 값으로는 어디가 늦는지 짚어 낼 수 없기 때문이다.

**지연은 감추지 않고 드러내는 것을 원칙으로 한다.** 늦어진 Task 는 주간 점검에서 반드시 목록에
올리고, 되찾을 방법이 없으면 일정을 다시 잡는다. 늦은 것을 늦게 알수록 되돌릴 수 있는 선택지가
줄어든다.

### 2.3 책임과 역할

진척 관리에 관여하는 사람의 몫을 발주와 수행으로 나누어 정리하면 다음과 같다.

| NO | 구분 | 직책 | 책임 및 역할 |
|---|---|---|---|
| 1 | 발주 | 프로젝트 총괄 | 범위와 일정을 승인하고, 자원을 지원하며, 주요 의사결정을 내린다 |
| 2 | 발주 | 현업 담당자 | 요구사항을 확정하고, 검증 기준에 합의하며, 전환 결과를 확인한다 |
| 3 | 발주 | 시스템 담당자 | 계정·권한·접속 환경을 제공하고, 전환 시점과 중단 시간을 협의한다 |
| 4 | 수행 | 프로젝트 관리자(PM) | 전체 일정과 진척을 관리하고, JIRA 를 운영하며, 이슈를 보고·격상한다 |
| 5 | 수행 | 데이터 이관 PL | 이관 대상과 방식을 설계하고, 이관 Task 를 분해해 진척을 관리한다 |
| 6 | 수행 | Application 전환 PL | 접속과 쿼리 전환을 설계하고, 전환 Task 를 분해해 진척을 관리한다 |
| 7 | 수행 | 개발자 | 맡은 Task 를 수행하고, 상태와 진척을 매일 갱신하며, 산출물을 만든다 |
| 8 | 수행 | DBA | WarehousePG 의 스키마·권한·성능을 맡고, 이관 적재를 지원한다 |
| 9 | 수행 | 품질 담당 | 검증 계획을 세우고 전후 결과를 대사하며, 결함을 등록·추적한다 |

**JIRA 를 갱신할 책임은 일을 맡은 사람에게 있다.** 관리자가 대신 상태를 바꿔 주기 시작하면 기록이
실제와 벌어지고, 그때부터 진척 보고는 현장을 비추지 못한다. PM 은 갱신을 대신하는 사람이 아니라
갱신되지 않은 Task 를 찾아내는 사람이다.

## 3. 품질 활동

### 3.1 개요

**이 프로젝트에서 품질은 "전환 전후의 결과가 같은가"로 판정된다.** 새로 만드는 기능이 없으므로 잘
만들었는지를 묻는 대신, 바꾸기 전과 똑같이 나오는지를 묻는다. 화면이 뜨고 쿼리가 돌아도 숫자가
전과 다르면 그것은 실패다.

**품질은 두 가지를 본다.** 하나는 **데이터 품질**로, Impala 에서 뽑아 WarehousePG 에 담은 데이터가
빠짐없이 그리고 틀림없이 들어갔는지다. 다른 하나는 **산출물 품질**로, 설계서와 이관 정의, 전환한
쿼리 같은 결과물이 정해진 기준을 지켰는지다. 둘 중 하나만 챙기면 반쪽이 되는데, 문서가 아무리
반듯해도 데이터가 어긋나면 소용이 없고 데이터가 맞아도 근거가 남지 않으면 다음에 되풀이할 수 없기
때문이다.

**품질 활동은 기획과 관리 두 갈래로 나눈다.** 기획은 착수할 때 한 번 하는 일로, 무엇을 어느 수준까지
맞출 것인지와 그것을 어떻게 확인할 것인지를 미리 정한다. 관리는 프로젝트가 끝날 때까지 되풀이하는
일로, 정해 둔 기준대로 확인하고 어긋난 것을 결함으로 잡아 끝까지 좇는다.

**기준을 먼저 정하는 이유는 분명하다.** 검증 기준을 나중에 정하면 이미 나온 결과에 맞춰 기준이
느슨해진다. 무엇을 통과로 볼지 미리 합의해 두어야 통과와 실패를 다투지 않는다.

**결함은 진척과 마찬가지로 JIRA 로 관리한다.** 검증에서 나온 어긋남은 결함 이슈로 등록해 담당과
기한을 붙이고, 고친 뒤 다시 검증해 닫는다. 별도 대장을 만들지 않는 이유는 2장에서 일정을 JIRA 로
모은 이유와 같다.

### 3.2 품질 기획

품질 기획은 착수 단계에서 여섯 절차로 진행한다. 여기서 정한 기준이 3.3 의 모든 확인 활동의 잣대가
되므로, 발주와 수행이 함께 합의하고 승인까지 마친 뒤에 다음 단계로 넘어간다.

| NO | 수행 절차 | 수행 내용 | 입력물 | 산출물 |
|---|---|---|---|---|
| 1 | 품질 목표 수립 | 무엇을 어느 수준까지 맞출지 정하고 수치로 적는다 | 프로젝트 관리 계획서, 범위 합의 내용 | 품질 목표서 |
| 2 | 품질 기준 정의 | 데이터 대사 기준과 산출물 검토 기준을 항목별로 정한다 | 품질 목표서, 요구사항 정의서 | 품질 기준서, 검토 점검표 |
| 3 | 검증 대상 선정 | 대사할 테이블과 비교할 화면·쿼리를 목록으로 확정한다 | 이관 대상 목록, 화면·기능 목록 | 검증 대상 목록 |
| 4 | 검증 방법 설계 | 대사 방법과 표본 추출 기준을 정하고 자동화 범위를 나눈다 | 검증 대상 목록, 품질 기준서 | 검증 방법서, 대사 쿼리 초안 |
| 5 | 품질 일정 수립 | 검토와 시험 시점을 일정 기준선에 넣고 담당을 지정한다 | 검증 방법서, 일정 기준선 | 품질 활동 일정, JIRA 품질 Task |
| 6 | 품질 계획 승인 | 발주와 수행이 함께 검토하고 승인해 기준을 확정한다 | 위 산출물 일체 | 승인된 품질 관리 계획서 |

**품질 목표는 숫자로 적는다.** "정확하게 옮긴다" 같은 말은 통과 여부를 가릴 수 없다. 이관 건수
일치율, 대사 항목의 값 일치율, 잔존 결함 수처럼 세어서 판정할 수 있는 형태로 적어 둔다.

**표본을 어떻게 뽑을지도 미리 정한다.** 전체를 한 건씩 맞춰 보는 것은 규모상 어려우므로, 건수와
합계는 전량으로 보고 값은 표본으로 본다. 표본을 어떤 기준으로 몇 건 뽑을지 정해 두지 않으면
검증했다는 말의 무게가 사람마다 달라진다.

### 3.3 품질 관리

품질 관리는 기획에서 정한 기준대로 확인하고 어긋난 것을 바로잡는 활동이며, 프로젝트가 끝날 때까지
여덟 절차로 되풀이한다. 1~2번은 만드는 동안, 3~6번은 검증 기간에, 7~8번은 주기와 종료 시점에 한다.

| NO | 수행 절차 | 수행 내용 | 입력물 | 산출물 |
|---|---|---|---|---|
| 1 | 산출물 검토 | 설계서와 이관 정의 등을 점검표로 검토하고 보완 후 승인한다 | 작성된 산출물, 검토 점검표 | 검토 결과서, 승인된 산출물 |
| 2 | 단위 검증 | 이관 Task 단위로 담은 건수와 값을 담당자가 확인한다 | 이관 실행 결과, 품질 기준서 | 단위 검증 결과, 결함 이슈 |
| 3 | 데이터 대사 | Greenplum 과 WarehousePG 의 건수·합계·표본 값을 맞춰 본다 | 검증 대상 목록, 대사 쿼리 | 대사 결과서, 불일치 목록 |
| 4 | 전환 시험 | 화면과 기능을 전후로 실행해 결과와 응답 시간을 비교한다 | 검증 방법서, 전환된 Application | 시험 결과서, 성능 비교표 |
| 5 | 결함 조치와 재검증 | 결함을 담당·기한과 함께 좇고, 고친 뒤 같은 방법으로 다시 확인한다 | 결함 이슈, 불일치 목록 | 조치 내역, 재검증 결과 |
| 6 | 사용자 확인 | 현업 담당자가 실제 업무 시나리오로 직접 확인한다 | 시험 결과서, 확인 시나리오 | 사용자 확인 결과서 |
| 7 | 품질 지표 집계·보고 | 대사 통과율과 결함 현황을 주기로 집계해 회의에 올린다 | 검증 결과 일체, 결함 이슈 | 주간 품질 보고서 |
| 8 | 품질 활동 완료 확인 | 목표 달성과 잔존 결함을 확인하고 전환 가능 여부를 판정한다 | 품질 목표서, 지표 집계 결과 | 품질 완료 확인서, 전환 승인 |

**대사는 세 겹으로 본다.** 건수가 맞는지, 합계 같은 집계값이 맞는지, 뽑은 표본의 값이 한 칸씩
맞는지다. 앞의 둘은 빠뜨린 데이터를 잡아내고 마지막 하나는 잘못 들어간 데이터를 잡아낸다. 건수만
맞춰 보고 넘어가면 값이 뒤틀린 것을 놓친다.

**결함은 고치는 것으로 끝내지 않고 다시 검증해 닫는다.** 고쳤다는 말과 고쳐졌다는 확인은 다르며,
재검증 기록이 없으면 나중에 같은 문제가 났을 때 언제부터 잘못됐는지 되짚을 수 없다.

**8번이 전환의 문지기다.** 품질 목표에 미치지 못하거나 심각한 결함이 남아 있으면 전환하지 않는다.
일정에 쫓겨 이 판정을 건너뛰면, 되돌리는 데 드는 비용이 미룬 기간보다 훨씬 커진다.

### 3.4 품질 보증

**품질 보증은 만든 것이 아니라 만드는 방식을 본다.** 3.3 의 품질 관리가 나온 결과물이 기준에
맞는지 확인하는 일이라면, 품질 보증은 그 확인이 정해진 절차대로 이루어지고 있는지를 확인하는
일이다. 대사를 통과했다는 기록이 있어도 정해진 표본 기준을 지키지 않고 뽑은 것이라면 그 통과는
믿을 수 없다.

**그래서 점검하는 사람을 만드는 사람과 분리한다.** 자기가 한 일을 자기가 점검하면 익숙해진 대로
넘어가기 쉽다. 프로젝트 수행 조직 안에 두더라도 품질 보증 담당은 개발과 이관 업무를 겸하지 않게
한다.

품질 보증은 여섯 절차로 진행하며, 정해진 시점마다 되풀이한다.

| NO | 수행 절차 | 수행 내용 | 입력물 | 산출물 |
|---|---|---|---|---|
| 1 | 보증 계획 수립 | 언제 무엇을 점검할지와 점검 항목을 정한다 | 품질 관리 계획서, 일정 기준선 | 품질 보증 계획서, 점검 체크리스트 |
| 2 | 프로세스 준수 점검 | 진척·검증·형상 절차가 정한 대로 돌아가는지 확인한다 | 점검 체크리스트, JIRA 기록 | 프로세스 점검 결과서 |
| 3 | 산출물 표준 점검 | 산출물이 정해진 양식과 작성 기준을 지켰는지 확인한다 | 승인된 산출물, 산출물 표준 | 산출물 점검 결과서 |
| 4 | 부적합 도출·시정 요구 | 어긋난 것을 부적합으로 기록하고 시정을 요구한다 | 점검 결과서 일체 | 부적합 보고서, 시정 요구서 |
| 5 | 시정 조치 확인 | 요구한 시정이 실제로 이루어졌는지 다시 확인한다 | 시정 요구서, 조치 내역 | 시정 확인 결과서 |
| 6 | 단계 품질 게이트 심사 | 다음 단계로 넘어가도 되는지 판정해 승인하거나 보류한다 | 품질 지표, 부적합 처리 현황 | 단계 이행 승인서 |

**부적합과 결함은 다르다.** 결함은 결과물이 틀린 것이고 부적합은 절차를 지키지 않은 것이다. 예를
들어 대사 결과가 틀렸다면 결함이고, 대사를 하기는 했는데 기록을 남기지 않았다면 부적합이다. 둘을
섞어 세면 어디를 고쳐야 하는지 알 수 없어 따로 관리한다.

**게이트 심사는 형식이 아니라 제동 장치다.** 통과하지 못하면 다음 단계로 넘어가지 않는다는 것이
지켜져야 심사에 의미가 생긴다.

### 3.5 결함 관리

**결함은 발견한 순간부터 닫힐 때까지 하나의 이슈로 좇는다.** 검증에서 나온 어긋남, 시험에서 나온
오동작, 사용자 확인에서 나온 지적을 모두 JIRA 결함 이슈로 등록하고 상태로 진행을 표시한다. 말로
전달하고 고치면 무엇이 남아 있는지 아무도 세지 못한다.

결함 관리는 일곱 절차로 돌아간다.

| NO | 수행 절차 | 수행 내용 | 입력물 | 산출물 |
|---|---|---|---|---|
| 1 | 결함 등록 | 발견한 어긋남을 재현 방법과 함께 이슈로 등록한다 | 검증·시험 결과, 사용자 지적 | JIRA 결함 이슈 |
| 2 | 분류와 심각도 판정 | 유형을 나누고 업무 영향에 따라 심각도와 우선순위를 매긴다 | JIRA 결함 이슈, 심각도 기준 | 심각도·우선순위가 매겨진 결함 |
| 3 | 원인 분석 | 데이터·쿼리·설정 중 어디에서 비롯됐는지 짚는다 | 결함 이슈, 실행 로그·대사 결과 | 원인 분석 기록 |
| 4 | 조치 계획과 담당 지정 | 고칠 방법과 담당자, 기한을 정해 이슈에 붙인다 | 원인 분석 기록, 일정 기준선 | 조치 계획, 담당·기한이 지정된 결함 |
| 5 | 결함 수정 | 정한 방법대로 고치고 무엇을 바꿨는지 남긴다 | 조치 계획, 대상 산출물·데이터 | 수정된 산출물, 변경 기록 |
| 6 | 재검증과 종료 | 처음 발견한 방법으로 다시 확인하고 통과하면 닫는다 | 수정 결과, 검증 방법서 | 재검증 결과, 종료된 결함 이슈 |
| 7 | 추이 분석·재발 방지 | 유형별 추이를 살펴 되풀이되는 원인을 없앤다 | 결함 이력 일체 | 결함 분석 보고서, 개선 조치 |

**심각도는 업무 영향으로 매긴다.** 고치기 어려운 정도가 아니라 그대로 두었을 때 업무가 얼마나
곤란해지는지로 나눈다. 숫자가 틀리는 결함은 화면이 느린 결함보다 언제나 앞선다.

**결함을 닫는 사람은 고친 사람이 아니라 발견한 쪽이다.** 고친 사람이 스스로 닫으면 재검증이
생략되기 쉽다. 재검증 기록 없이 닫힌 결함은 닫힌 것이 아니다.

**남은 결함은 숨기지 않고 전환 판정에 올린다.** 심각도별로 몇 건이 남았는지를 그대로 보고하고,
남은 채로 전환할지 말지는 3.3 의 완료 확인에서 판정한다.

### 3.6 책임과 역할

품질 활동에 관여하는 사람의 몫을 발주와 수행으로 나누어 정리하면 다음과 같다.

| NO | 구분 | 직책 | 책임 및 역할 |
|---|---|---|---|
| 1 | 발주 | 프로젝트 총괄 | 품질 목표와 기준을 승인하고, 전환 여부를 최종 판정한다 |
| 2 | 발주 | 현업 담당자 | 검증 기준에 합의하고, 사용자 확인을 수행하며, 결과를 승인한다 |
| 3 | 발주 | 품질 담당 | 발주 측 관점에서 품질 활동과 산출물을 점검하고 의견을 낸다 |
| 4 | 수행 | 프로젝트 관리자(PM) | 품질 계획을 총괄하고 자원을 배정하며, 부적합·결함 처리를 챙긴다 |
| 5 | 수행 | 품질 보증 담당(QA) | 절차 준수와 산출물 표준을 독립적으로 점검하고 게이트를 심사한다 |
| 6 | 수행 | 품질 관리 담당(QC) | 검증 계획을 세우고 대사와 시험을 수행하며, 결함을 등록·추적한다 |
| 7 | 수행 | 데이터 이관 PL | 이관 데이터의 정확성을 책임지고, 대사에서 나온 결함을 조치한다 |
| 8 | 수행 | Application 전환 PL | 전환한 화면과 쿼리의 동작을 책임지고, 시험 결함을 조치한다 |
| 9 | 수행 | 개발자 · DBA | 맡은 부분을 검증 기준에 맞게 만들고, 배정된 결함을 고쳐 재검증에 넘긴다 |

**품질 보증 담당은 만드는 일을 겸하지 않는다.** 겸하면 자기 일을 자기가 점검하게 되어 점검이
형식으로 흐른다. 조직 사정상 완전히 나누기 어렵다면, 적어도 자기가 만든 산출물은 다른 사람이
점검하도록 배정한다.
