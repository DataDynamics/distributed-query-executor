# 데이터 아키텍처 정의서

> **이 파일은 목차 초안이다.** 각 절에는 무엇을 쓸지만 한 줄로 적어 두었고 본문은 아직 없다.
> 목차가 확정되면 이 안내와 각 절의 한 줄 메모를 지우고 내용으로 채운다.

이 문서는 이 시스템을 **데이터 관점**에서 정리한 데이터 아키텍처 정의서다. 어떤 데이터가 어디서
어디로 흐르고, 그중 무엇을 이 시스템이 소유하며, 그 데이터를 어떤 표준과 규칙으로 다루는지를 다룬다.

같은 디렉터리의 다른 문서와 역할이 갈린다. SW 의 구조와 그 적용은 SW 아키텍처 정의서가, 인프라와
운영은 기술 아키텍처 정의서가 맡는다. 메타 테이블의 ER 그림은 `er-diagram.md` 에, 컬럼 단위 명세는
`tables.md` 에 이미 있으므로 여기서는 그 표를 다시 옮기지 않고 **무엇을 왜 기억하는가**를 데이터
관점에서 해석한다. 겹치는 사실을 바꿀 때는 관련 문서를 함께 고친다.

시스템은 데이터를 소유하지 않고 **옮기는** 것이 존재 이유라 아래와 같이 바꿨다.

# I. 개요

## 1. 목적과 범위

> 이 문서가 답하는 질문과 다루지 않는 것(옮기는 데이터의 업무적 의미, 대상 시스템의 데이터 모델).

## 2. 이 시스템의 데이터 관점

> 데이터를 소유하지 않고 흐르게 한다는 전제와, 그 전제가 이 문서 전체의 서술을 어떻게 가르는지.

## 3. 데이터 아키텍처 원칙

> 데이터는 coordinator 를 지나지 않는다, 통과 데이터는 해석하지 않는다, 중간 데이터는 언제든 버릴
> 수 있어야 한다, 무엇을 읽어 무엇을 넣었는지는 반드시 남는다 — 네 가지 원칙과 그 근거.

---

# II. 데이터 아키텍처 정의

## 1. 데이터 영역 구분

### 1.1 이관 데이터

> 소스에서 읽어 대상에 넣는 통과 데이터. 소유하지 않고 보관하지 않으며 스키마는 요청이 정한다.

### 1.2 메타 데이터

> 이 시스템이 소유하는 유일한 데이터. job 상태와 실행 이력, executor 상태·예약·헬스 메트릭 일곱
> 테이블의 성격과 각각이 답하는 질문.

### 1.3 중간 데이터

> 스테이징 CSV 와 S3 객체, TEMP 테이블과 외부테이블. 실행 중에만 존재하며 실패해도 재실행으로
> 복구된다.

## 2. 데이터 아키텍처 구성도

> 세 영역과 그 사이의 흐름을 한 장으로. 새 그림(data-domains)을 그린다.

## 3. 데이터 소유와 책임 경계

> 무엇이 이 시스템의 책임이고 무엇이 소스·대상·기관 표준의 책임인지. 백업 범위와 보존 정책이
> 갈리는 지점.

---

# III. 데이터 표준

## 1. 식별자 표준

> job_id 와 task_id 의 형식과 생성 시점, 멱등 키와 요청 지문(sha256), 스테이징 객체와 job 고유
> 외부테이블의 이름 규칙.

## 2. 시각 표준

> 타임존 없는 KST timestamp 로 통일한 이유와 그 적용 범위(메타 테이블 기본값·로그·API 응답),
> 다른 타임존 값이 들어올 때의 처리.

## 3. 문자와 인코딩 표준

> UTF-8 고정, 한글이 섞인 데이터에서 주의할 지점.

## 4. CSV 형식 표준

> 구분자·NULL 표현·인용문자의 기본값과 요청별 재정의. 기본 구분자로 백틱을 쓰는 이유와, executor
> 의 write 설정과 외부테이블 FORMAT 이 같은 값을 공유해야 하는 이유.

## 5. 타입 처리 표준

> 소스에서 읽을 때 형변환을 끄고 wire 문자열을 그대로 받는 이유, 결측값(NaN·NaT·pd.NA·inf)을 CSV
> NULL 마커로 떨구는 규칙, numpy 스칼라를 낮추지 않으면 컬럼 타입별로 결과가 갈리는 함정.

## 6. 명명 규칙

> 메타 테이블의 스키마 한정 규칙과 설정·DDL 두 곳을 함께 고쳐야 하는 이유, 스테이징 테이블과
> 외부테이블의 이름이 job·task 로 격리되는 규칙.

---

# IV. 데이터 모델

## 1. 개념 데이터 모델

> job·task·executor·coordinator 네 개념과 그 사이의 관계. 무엇을 기억하기로 했고 무엇을 기억하지
> 않기로 했는가.

## 2. 논리 데이터 모델

> 개념을 엔터티와 관계로 옮긴 모습. 상태를 담는 것과 이력을 담는 것을 나눈 이유.

## 3. 물리 데이터 모델

### 3.1 PostgreSQL

> 실제 테이블 일곱 개와 키·인덱스의 의도. JSONB 로 job 본문을 담은 이유와 멱등 키 부분 유일 인덱스.

### 3.2 WarehousePG

> 분산키가 붙으면서 달라지는 것. 대리 키를 빼고 co-locate 하는 이유와 멱등 선점이 best-effort 가
> 되는 제약.

## 4. 이관 데이터의 스키마 계약

> 이관 데이터에는 모델이 없고 계약만 있다. 요청이 정하는 것(대상 테이블·컬럼·파티션 컬럼·적재
> 방식)과 시스템이 보는 것(SELECT 의 컬럼 순서와 개수), 어긋났을 때 어디서 걸러지는가.

# V. 데이터 흐름

## 1. data plane 과 control plane 의 분리

> 데이터는 executor 가 직접 흘려보내고 coordinator 에는 상태와 행 수만 올라온다는 것, 그 분리가
> 데이터 관점에서 뜻하는 것.

## 2. 하나의 SELECT 가 N 개로 갈리는 방식

### 2.1 파티션 IN 분할

> IN 목록을 N 등분하는 두 방식과 원문 포맷을 보존한 채 치환하는 이유.

### 2.2 날짜 fan-out

> 구간의 두 끝을 파라미터로 받아 하루를 task 하나로 펼치는 방식과 그 데이터 경계.

## 3. exec_mode 별 데이터 경로

> 다섯 가지 경로에서 데이터가 어디를 거치는지. 곧장 넣는 것과 staging 을 거치는 것, 파일을 만들어
> 대상이 당겨 읽는 것의 차이.

## 4. 2단계 적재의 데이터 흐름

> Phase 1 에서 만들어지는 파일의 단위와 배치, barrier 뒤 Phase 2 에서 하나의 외부테이블로 묶여
> 들어가는 과정, Phase 3 의 정리.

## 5. 소스 다양성과 데이터 정규화

> 커서를 주지 않는 소스의 반환 형태를 하나로 맞추는 방식과, 미리보기용 함수와 이관용 함수의 계약이
> 다른 이유.

---

# VI. 데이터 정합성과 품질

## 1. 정합성이 결정되는 지점

> 접수·분할·적재·집계 네 지점에서 각각 무엇이 보장되고 무엇이 보장되지 않는가.

## 2. 재실행 안전성

> 요청 멱등과 데이터 멱등 두 층위. overwrite_partitions 가 멱등을 만드는 방식과 append 가 그렇지
> 않은 이유, 날짜 fan-out 이 append 뿐이라 생기는 제약.

## 3. 분할의 정확성

> 분할이 원본 집합을 빠짐없이 겹치지 않게 덮는다는 보장과, 그것이 깨지는 알려진 경로(부호 변수를
> 쓰지 않는 템플릿에서의 조용한 중복 적재)와 방어.

## 4. 적재 결과 검증

> row count 를 어디서 세어 어디로 올리는지, COPY 전 컬럼 사전검증, PARTIAL 이 성공이 아니라는 것,
> 사람이 대상에서 직접 확인하는 절차.

## 5. 품질이 조용히 깨지는 경로

> 결과가 잘린 채 적재되는 경우, 결측값이 문자열로 들어가는 경우, MockBackend 로 떠서 아무것도
> 넣지 않는 경우 — 증상과 판별법.

# VII. 데이터 보안

## 1. 데이터 등급과 취급 원칙

> 통과 데이터를 보관하지 않는 것이 곧 노출면을 줄이는 것이라는 점과, 그럼에도 남는 흔적.

## 2. 전송 구간 보호

> 소스 구간의 TLS 와 인증, 대상 구간이 망 분리를 전제로 하는 것, 외부에 열리는 포트.

## 3. 비밀 정보와 마스킹

> 접속 정보를 두는 자리와 권한, 로그·대시보드·API 응답에서 가려지는 것.

## 4. 감사 추적

> 어떤 데이터소스에 어떤 문장을 던졌는지가 항상 남는다는 것과 그 기록의 범위·한계(절단 표기).

---

# VIII. 데이터 수명주기

## 1. 중간 데이터

> 언제 생겨 언제 지워지는가. 정리를 끄면 남는 것과 실패했을 때 남는 것, 사람이 치우는 방법.

## 2. 메타 데이터

> 앱이 오래된 행을 지우지 않는다는 것과, 그래서 보존 기간을 운영에서 걸어야 한다는 것.

## 3. 로그

> 일 단위 롤링과 보존 일수, 실행 SQL 기록이 로그 크기에 주는 영향.

## 4. 백업 범위

> 백업하는 것과 하지 않는 것, 옮긴 데이터가 이 시스템의 백업 범위 밖인 이유.

---

# IX. 데이터 용량 산정

## 1. 메타 데이터 증가량

> job 하나와 task 하나가 남기는 행 수와 대략의 크기, 헬스 메트릭이 주기로 쌓이는 양.

## 2. 중간 데이터의 순간 최대량

> 동시에 도는 task 수와 배치 크기로부터 스테이징이 차지하는 최대 용량을 잡는 방법.

## 3. 메모리에 올라가는 데이터

> 스트리밍이 메모리를 일정하게 유지하는 구조와, 청크를 쓰지 않는 커스텀 소스에서 전량이 올라가는
> 예외.
