# SW 아키텍처 정의서

이 문서는 이 시스템의 **소프트웨어를 어떤 구조로 나눴고, 그 구조가 실제 코드에 어떻게 적용됐으며,
바깥의 무엇과 어떻게 이어지는지**를 다룬다. 표준 양식을 이 시스템에 맞게 고쳐 썼다.

장비와 네트워크 이야기는 같은 디렉터리의 **기술 아키텍처 정의서**가 맡는다. 하드웨어, 네트워크,
설치할 소프트웨어 목록, 백업과 보안, 한 대가 죽었을 때의 대비가 그쪽에 있다. 이 문서는
**소프트웨어의 구조와 그 적용**에만 집중한다. 두 문서에 겹치는 사실이 있다면 바꿀 때 함께 고친다.

그림은 `images/` 아래에 있는 것을 그대로 가져다 쓴다. 같은 사실을 두 번 그리지 않기 위해서이며,
필요한 그림이 없을 때만 새로 그린다.

# I. 개요

## 1. 배경

### 원래 어떻게 하고 있었나

Impala 에 쌓인 데이터를 Greenplum 으로 옮기는 일은 원래 사람이 한 건씩 처리했다. `SELECT` 를 짜서
결과를 파일로 받고 그 파일을 목적지에 넣는 식이다.

이 방식에는 세 가지 문제가 있었다.

- **느리다.** 데이터가 한 줄기로만 흐르므로 양이 커지면 몇 시간을 붙잡고 있어야 했다.
- **다시 하기 어렵다.** 중간에 끊기면 어디까지 들어갔는지 알 수 없어 처음부터 다시 해야 했다.
- **막을 방법이 없다.** 여러 건을 동시에 돌리면 원본과 목적지가 함께 흔들리는데 그것을 제어할 장치가
없었다.

### 이 시스템은 어떻게 푸는가

셋으로 나눠 푼다.

**첫째, 쿼리 하나를 여러 조각으로 쪼개 동시에 읽는다.** 파티션 값을 기준으로 N 등분해 여러 서버가
나눠 읽으므로, 한 줄기로 흐르던 한계가 사라진다.

**둘째, 상태를 한곳에 모은다.** 지금 몇 개가 끝났고 무엇이 실패했는지를 언제든 볼 수 있고, **실패한
조각만 골라 다시 돌릴 수 있다.**

**셋째, 입구에서 받아 줄지 판단한다.** 원본과 목적지가 감당할 수 있는 만큼만 받아들이고 넘치면
거절한다.

### 환경이 준 제약

여기에 운영 환경의 제약이 더해졌고, 이 제약들이 구조의 모양을 상당 부분 결정했다.

- **외부 인터넷이 막혀 있다.** 실행 중에 바깥에서 무언가를 받아 올 수 없다.
- **운영체제가 주는 파이썬을 그대로 써야 한다.** 최신 버전을 요구하는 라이브러리를 쓸 수 없다.
- **목적지가 MPP 다.** 여러 서버가 데이터를 나눠 갖는 구조라, 대표 서버 한 곳으로 밀어 넣으면 그 한
대가 전체 속도의 한계가 된다.

## 2. 목표 시스템 구성도

### 2.1 목표 어플리케이션 구성도

구성은 단순하다. **coordinator 한 대가 요청을 받아 나누고, executor 여러 대가 실제로 데이터를
옮긴다.**

여기서 가장 중요한 것은 **데이터가 coordinator 를 지나지 않는다**는 점이다. executor 가 원본에서
읽어 목적지로 곧장 보낸다. 그래서 executor 를 늘리면 처리량이 그만큼 늘고, coordinator 는 지시와
상태만 다루므로 부담이 거의 늘지 않는다.

![목표 어플리케이션 구성도](images/architecture.svg)

### 2.2 목표 시스템 구성

| 구성요소 | 역할 | 수량 | 비고 |
|---|---|---|---|
| coordinator | 요청 접수, 검증과 분할, admission, 디스패치, 상태 집계 | 1대(가용성이 필요하면 N대) | 상태를 메모리에 두므로 단일 워커 |
| executor | 소스 읽기와 대상 적재, task 상태 관리 | N대 | 처리량은 이 수로 늘린다 |
| 메타 저장소 | 공유 job 저장소와 실행 이력, 상태·예약·메트릭 | 1식 | PostgreSQL. 단일 coordinator 면 선택 |
| 소스 | 이관할 데이터를 읽는 엔진 | 기존 시스템 | Impala 기본, Trino·사내 API 확장 |
| 적재 대상 | 옮긴 데이터가 들어가는 곳 | 기존 시스템 | Greenplum 계열 |
| 스테이징 매체 | 2단계 적재에서 CSV 를 두는 곳 | 선택 | S3 또는 세그먼트 로컬 디스크 |
| 운영자 CLI | 사람이 직접 소스·대상·S3 를 다루는 도구 | 서비스와 같은 트리 | 서비스와 설정을 공유 |

# II. SW 아키텍처 정의

## 1. 시스템간 업무적 연관 관계 관점

### 1.1 이관 요청 업무 관점

일을 맡기는 쪽은 대개 사람이 아니라 **업무 시스템이나 스케줄러**다.

예를 들어 하루치 매출을 정해진 시각에 옮겨야 한다고 하자. 스케줄러가 `POST /jobs` 를 호출하고,
응답으로 받은 작업 번호로 "끝났니?"를 물어보다가, 끝나면 다음 단계로 넘어간다. 요청과 조회는 모두
**coordinator 한 곳으로만** 가고, 뒤에 executor 가 몇 대 있는지는 알 필요가 없다.

업무 시스템이 SQL 전문을 들고 있지 않아도 되도록 **템플릿**을 둔다. 쿼리를 서버에 미리 등록해 두면
요청은 이름과 값만 보내면 된다. 그래서 **테이블 구조나 적재 규칙이 바뀌어도 호출하는 쪽 코드는
그대로 둘 수 있다.** 기간을 다루는 이관이라면 값 두 개로 구간을 주기만 하면 하루씩 나눠 돈다.

여기서 반드시 지켜야 하는 약속이 둘 있다.

**첫째, 접수와 완료는 다르다.** `202` 라는 응답은 "받았다"는 뜻일 뿐이다. 실제 결과는 따로 물어봐야
알 수 있고, **온전한 성공은 `DONE` 하나뿐이다.** `PARTIAL` 은 일부만 들어간 상태이므로 성공으로
다루면 안 된다.

**둘째, 다시 보낼 때를 대비해야 한다.** 응답을 못 받아 그냥 다시 보내면 같은 이관이 두 번 돌 수
있다. 그래서 **중복 방지 열쇠**를 함께 보낸다. 그리고 데이터가 두 번 들어가면 곤란한 업무라면, 넣기
전에 그 자리를 지우고 넣는 방식을 고른다.

### 1.2 운영·관제 업무 관점

운영자가 하는 일은 크게 셋이다.

**첫째, 살아 있는지 본다.** 전체 상태를 한 번 조회하면 executor 가 다 붙어 있는지, 일이 쌓이고
있는지, 자원이 남아 있는지가 함께 나온다. 브라우저를 쓸 수 있으면 화면으로 보고, 터미널만 있으면
같은 정보를 터미널에 그려 주는 도구로 본다.

**둘째, 실패를 좇는다.** 사용자가 작업 번호를 들고 오면 그 하나로 상태와 실패한 조각을 확인하고,
같은 번호로 로그를 모은다. **모든 로그 줄에 작업 번호와 조각 번호가 붙고 실행한 SQL 이 함께 남기
때문에**, 원본에서 못 읽은 것인지 목적지에 못 넣은 것인지를 가릴 수 있다. 필요하면 셸로
데이터베이스에 직접 물어본다.

**셋째, 용량을 조절한다.** 요청이 거절되기 시작하면 어느 단계가 좁은지 가려서 입구를 넓히거나
executor 를 늘린다. 값들이 서로 어긋나지 않는지는 설정 편집기가 곱셈을 풀어 보여 준다.

## 2. 시스템간 SW 기술 구조 관계 관점

### 2.1 SW 기술 유형 관점

이 시스템의 소프트웨어는 세 갈래로 나뉜다. 나눈 기준은 어떤 언어로 만들었는가가 아니라 **무엇을
책임지는가**다.

| 유형 | 책임 | 적용 구성요소 | 대표 기술 |
|---|---|---|---|
| API·제어 | 요청을 받아 검증·분할하고 admission 으로 받을지 판단해 디스패치하며 상태를 집계한다 | coordinator | FastAPI · asyncio · sqlglot · Jinja2 |
| 실행·적재 | 소스에서 읽어 대상에 넣고 그 진행을 보고한다 | executor | impyla · psycopg · boto3 · 스레드 풀 |
| CLI·운영 도구 | 사람이 터미널에서 직접 조회하고 정리한다 | `bin/` 도구 셋 · 설정 TUI · 모니터 | argparse · curses · 표준 라이브러리 |

세 갈래는 **설정과 로그 규칙을 함께 쓴다.** 같은 `config.properties` 를 읽고 같은 방식으로 로그를
남긴다. 그래서 **접속 정보를 한 곳만 고치면 서비스와 도구가 함께 따라온다.** 두 곳에 적어 두고
한쪽만 고쳐서 어긋나는 사고가 없다.

### 2.2 솔루션 배치 관점

무엇을 어느 서버에 설치할지는 **그 서버가 무슨 일을 하느냐**가 정한다.

가장 눈에 띄는 것은 **원본에 접속하는 드라이버를 executor 에만 둔다**는 점이다. coordinator 는
원본에 접속하지 않으므로 그 드라이버가 필요 없다. 그 덕에 coordinator 서버에는 그 드라이버를 설치할
때 필요한 개발 도구들도 들어가지 않아, 설치가 그만큼 가벼워진다.

| 노드 | 놓이는 것 | 이유 |
|---|---|---|
| coordinator | FastAPI · uvicorn · sqlglot · Jinja2 · httpx · psycopg | 요청 처리와 SQL 검증·렌더, 상태 저장 |
| executor | 위에 더해 impyla · thrift-sasl · pure-sasl · boto3 | 소스 읽기와 대상 적재, 스테이징 업로드 |
| 메타 저장소 노드 | PostgreSQL | 공유 상태와 이력 |
| 적재 대상 노드 | Greenplum · PXF(선택) | 외부테이블로 스테이징을 당겨 읽을 때만 PXF |
| 운영자 단말 | 없음 | 도구는 서비스 트리 안에서 실행한다 |

## 3. 시스템간 인프라 구성 관점

### 3.1 개발환경 관점

**개발은 실제 데이터베이스 없이 한다.** 이 점이 이 시스템을 다루기 쉽게 만드는 가장 큰 요소다.

원본과 목적지 접속 정보가 없으면, 아무것도 읽고 쓰지 않는 가짜 구현(`MockBackend`)으로 뜬다.
테스트는 그 가짜 구현과 가짜 실행기(`FakeRunner`)로 전 구간을 돈다. 그래서 **노트북에서도** 검사와
분할, 요청 수용 판단, 상태 변화, 화면, 로그까지 모두 확인할 수 있다.

```bash
python3.9 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q                      # 실제 DB 불필요
PYTHONPATH=src QUERY_EXECUTOR_CONFIG_DIR=config .venv/bin/python -m coordinator
COORDINATOR_EXECUTOR_MODE=local … -m coordinator   # executor 없이 한 프로세스로
```

두 가지가 개발을 특히 편하게 한다.

**local 모드** — executor 를 따로 띄우지 않고 coordinator 안에서 직접 실행한다. 설정이나 쿼리가
의도대로 도는지만 보고 싶을 때 프로세스 하나만 띄우면 된다.

**템플릿 자동 다시 읽기** — 쿼리 파일을 고칠 때마다 서비스를 껐다 켜지 않아도 된다.

### 3.2 운영환경 배포 관점

운영에서는 **coordinator 와 executor 를 한 디렉터리에 함께 설치하고, 실행할 때 역할을 나눈다.** 설치
파일이 두 벌일 필요가 없다.

설치 스크립트는 서비스 계정과 실행 환경, 실행 스크립트를 만든다. 그런데 설정과 템플릿, 사용자 정의
코드는 **아직 없을 때만** 넣는다.

왜 그럴까. 운영자가 채워 넣은 접속 정보와 인증서를 **재설치가 지워 버리면 안 되기 때문**이다. 대신
그 대가가 있다. **새 버전이 바꾼 기본값은 자동으로 반영되지 않으므로 손으로 옮겨야 한다.**

외부 인터넷이 막힌 환경이 전제이므로 설치는 미리 받아 둔 꾸러미로 한다. API 설명서 화면과 글꼴을
포함한 파일도 모두 설치 디렉터리 안에 넣어 두어 실행 중에 바깥으로 나가지 않는다. 서비스를 켜는 것은
스크립트가 기본이고, 운영체제의 서비스 관리 기능으로 돌릴 설정 파일도 함께 배포한다.

# III. SW 아키텍처 상세 정의

## 1. SW 기술 구조 유형 정의

### 1.1 아키텍처 영향 요소 정리

구조를 이렇게 만든 이유는 대부분 **환경의 제약**에서 나왔다. 좋은 설계를 고민해서 나온 것이 아니라,
그렇게 할 수밖에 없었던 사정이 있었다는 뜻이다. 아래 표의 왼쪽이 그 사정이고 오른쪽이 그것이 설계에
남긴 흔적이다.

| 영향 요소 | 제약 | 설계에 준 영향 |
|---|---|---|
| 에어갭 | 런타임에 외부로 나갈 수 없다 | 웹 에셋과 API 문서를 트리에 내장, 설치는 오프라인 휠 |
| 운영체제 파이썬 | RHEL 9.2 기본 3.9 를 그대로 쓴다 | 3.10 이상을 요구하는 패키지 버전에 상한을 둔다 |
| 적재 대상이 MPP | 마스터로 밀어 넣으면 한 노드가 ceiling 이 된다 | 파일을 만들어 세그먼트가 당겨 읽는 2단계 경로를 둔다 |
| 대용량 스트리밍 | 결과 전체를 메모리에 올릴 수 없다 | 배치 단위 스트리밍과 읽기·쓰기 파이프라인 |
| 소스 다양성 | 커서를 주지 않는 사내 API 도 소스가 된다 | 커서처럼 감싸는 어댑터를 두어 읽기 루프를 고정 |
| 상태가 메모리 | 프로세스가 상태를 들고 있다 | 단일 워커로 실행하고 확장은 인스턴스 수로 |
| 운영자 편집 자산 | 설정·템플릿·커스텀은 사람이 고친다 | 재설치가 덮지 않고 최초 1회만 시딩 |
| 단일 리전 | 시각이 KST 하나뿐이다 | 타임존 없는 KST 시각으로 통일 |
| 감사 요구 | 무엇을 읽어 무엇을 넣었는지 남아야 한다 | 실행 SQL 을 레벨과 무관하게 항상 기록 |

### 1.2 SW 기술 구조 유형 정의

**API·제어** 갈래는 **요청을 받아 판단하는 쪽**이다. 검사하고, 쪼개고, 받아 줄지 정하고, 나눠 주고,
결과를 모은다. **데이터에는 손대지 않는다.** 판단이 빨라야 하므로 한 가지 일에 붙들려 있지 않는
방식으로 돌고, 무거운 일은 모두 아래 갈래에 넘긴다.

**실행·적재** 갈래는 **데이터를 실제로 옮기는 쪽**이다. 원본에서 묶음 단위로 읽어 목적지에 넣고 진행
상황을 보고한다. 여기서 쓰는 데이터베이스 드라이버는 일이 끝날 때까지 붙들려 있는 종류라, 별도의
실행 흐름으로 넘겨 전체가 멈추지 않게 한다. 옮기는 방식은 여러 갈래지만 **바깥에서 보는 모습은
하나로 맞췄다.**

**CLI·운영 도구** 갈래는 **사람이 직접 쓰는 쪽**이다. 서비스와 같은 설정을 읽지만 수명이 명령 한
번이다. 그리고 사람이 보고 있는지 아닌지에 따라 행동을 바꾼다. **자동 실행에 걸어 두었을 때 멈추거나
깨지지 않는 것**이 이 갈래의 핵심 요구다.

## 2. API·제어 SW 기술 구조

### 2.1 API·제어 SW 기술 구조 정의

#### 2.1.1 모듈 구조 관점

모듈은 **요청이 지나가는 순서대로** 나뉜다. 코드를 찾을 때 이 순서를 떠올리면 대개 맞다.

| 하는 일 | 맡는 모듈 |
|---|---|
| 요청을 받고, 중복인지 확인하고, 날짜별로 펼친다 | 앱 계층 |
| SQL 이 규칙에 맞는지 검사한다 | 파서 |
| 여러 조각으로 쪼갠다 | splitter |
| 등록된 쿼리로 SQL 을 만든다 | 템플릿 엔진 |
| 받아 줄지 판단하고 일감을 나눠 준다 | dispatcher |
| 상태 저장, 기록, 상태 감시, executor 고르기 | 각각 별도 모듈 |

화면을 그리는 부분은 **API 를 읽기만 하므로** 처리 흐름에 끼어들지 않는다. 화면을 꺼도 이관은 그대로
돈다.

#### 2.1.2 런타임 구성 관점

**한 프로세스 안에서 일꾼 하나로만 돈다.** 보통 웹 서버는 일꾼을 여럿 두어 요청을 나눠 처리하는데,
여기서는 그러지 않는다.

이유는 상태를 프로세스 메모리에 들고 있기 때문이다. 일꾼을 늘리면 **같은 작업을 두 일꾼이 서로
다르게 알게 된다.** 그래서 처리량을 늘릴 때는 일꾼이 아니라 서버 대수를 늘린다.

요청을 처리할 때는 **"그 자리에서 끝내는 구간"과 "뒤로 넘기는 구간"의 경계가 뚜렷하다.**

검사와 분할, 받아 줄지 판단까지는 요청을 처리하는 함수 안에서 끝낸다. 잘못된 요청을 곧바로 되돌려
주기 위해서다. 실제 실행은 응답을 보낸 뒤 뒤에서 시작한다. 뒤에서는 자기 차례를 기다렸다가 조각들을
한꺼번에 띄우고 상태를 주기적으로 확인한다.

여기에 작은 배려가 하나 있다. 데이터베이스를 부르는 일은 별도의 실행 흐름으로 넘기는데, **그때 작업
번호를 함께 들려 보낸다.** 그러지 않으면 그 흐름이 남기는 로그에 작업 번호가 붙지 않아, 어느 작업의
쿼리인지 알 수 없게 된다.

#### 2.1.3 배포 관점

배포하는 단위는 **디렉터리 하나**이고, 역할은 실행할 때 갈린다.

설정은 **기동할 때 한 번 읽어 메모리에 굳는다.** 그래서 값을 바꾸면 서비스를 다시 띄워야 반영된다.

기동할 때 화면에 뜨는 안내에는 **실제로 읽은 설정 파일의 전체 경로**가 찍힌다. 엉뚱한 디렉터리의
설정을 읽고 있는 사고를 그 자리에서 잡아내기 위한 것이다.

화면은 설정으로 끌 수 있다. 화면을 열어 두기 곤란한 환경에서도 서비스만 띄울 수 있다.

### 2.2 API·제어 SW 기술 구조 상세설계

#### 2.2.1 구조 개요

요청이 들어와 끝날 때까지의 흐름은 이렇다.

1. 중복 방지 열쇠를 먼저 확인한다
2. 템플릿을 쓰는 요청이면 여기서 SQL 을 만든다
3. 그 SQL 이 규칙에 맞는지 검사한다
4. 파티션 값 목록을 N 등분해 조각을 만든다
5. 받아 줄지 판단한다
6. 통과하면 작업을 만들면서 열쇠를 **한 번의 동작으로 선점하고** `202` 를 돌려준다
7. 뒤에서 자기 차례를 잡아 실행 상태로 올리고 조각들을 내보낸다
8. 모두 끝나면 결과를 모아 최종 상태를 정한다

![시퀀스 — POST /jobs 접수](images/seq-create-job.svg)

#### 2.2.2 구성 요소

| 구성 요소 | 역할 | 주요 인터페이스 |
|---|---|---|
| 앱 계층 | 라우팅, 멱등 사전확인과 재생, 날짜 fan-out, 응답 조립 | `POST /jobs` · `GET /jobs/{id}` · `POST /query-execute` |
| 파서 | SELECT 검증과 파티션 `IN` 절 탐색 | `validate_and_parse()` |
| splitter | 값 목록을 N 등분하고 원문 포맷을 보존해 치환 | `split()` · `wrap()` |
| 템플릿 엔진 | manifest 와 `.sql.j2` 를 렌더해 SQL 필드를 채움 | `render()` · `render_query()` |
| admission | 실행 슬롯과 대기 큐 관리, 초과 시 거절 | `try_admit()` · `slot()` |
| dispatcher | 수명주기와 디스패치, 폴링, 취소, 2단계 적재의 Phase 2 | `run()` · `_execute()` |
| 저장소 | job 상태 보관과 멱등 키 선점 | `claim_and_add()` · `save()` · `get()` |
| 이력·모니터 | 상태 전이 기록, executor 헬스와 메트릭 수집 | `record()` · `snapshot()` |

#### 2.2.3 구조 상세 설계

**과부하를 막는 장치가 세 겹으로 겹쳐 있다.**

맨 앞에서 동시에 실행할 작업 수와 대기 줄의 길이를 제한한다. 그 아래에서 coordinator 가 한꺼번에
내보낼 조각 수를 제한한다. 다시 그 아래에서 executor 한 대가 동시에 돌릴 조각 수를 제한한다.

여기서 기억할 것이 있다. **실제 한계는 언제나 가장 좁은 층이 정한다.** 맨 앞의 값을 아무리 키워도
아래층이 좁으면 소용이 없다.

![과부하 방어는 세 층으로 겹친다](images/admission.svg)

**"두 번 돌려도 안전한가"는 두 층위로 나뉜다.** 둘은 별개이고 각각 따로 켜야 한다.

**요청 층위** — 같은 열쇠에 같은 내용이 오면 새로 만들지 않고 기존 작업을 그대로 돌려준다. 같은
열쇠에 다른 내용이 오면 거절한다. 클라이언트가 응답을 못 받아 재시도하는 흔한 상황을 흡수한다.

**데이터 층위** — 넣기 전에 담당 자리를 지우고 넣는다. 그래서 몇 번을 다시 돌려도 결과가 같다. 다만
이것은 **옮기는 방식이 지원할 때만** 성립한다. 그냥 덧붙이는 방식은 다시 돌리면 그만큼 더 쌓인다.

**상태는 한 방향으로만 움직인다.** 대기 → 분할 → 실행 → 종료 순이고 되돌아가지 않는다.

최종 상태는 이렇게 정해진다. 취소된 것이 있으면 취소가 우선이다. 실패가 하나도 없으면 완료, 일부만
성공했고 정책이 허용하면 부분 성공, 그 밖은 실패다.

**날짜를 하루씩 펼치는 기능에는 반드시 지켜야 할 약속이 하나 있다.**

이 기능은 구간의 시작과 끝을 값으로 받아 하루를 조각 하나로 펼친다. 그런데 템플릿이 정해진 변수를
쓰지 않으면, **각 조각이 의도보다 넓은 구간을 읽어 같은 데이터가 여러 번 들어간다.** 게다가 오류
없이 성공으로 끝나기 때문에 나중에 건수를 세어 보기 전에는 알아채기 어렵다.

그래서 SQL 을 만들기 전에 템플릿을 검사해, 그 변수를 쓰지 않으면 **접수 단계에서 거절한다.** 경고가
아니라 거절인 이유가 여기에 있다.

**2단계로 넣는 방식에서 두 번째 단계는 coordinator 가 중앙에서 한다.** executor 는 파일을 만들어
두는 데까지만 하고, 그 파일을 목적지가 읽게 만들어 넣고 정리하는 일은 coordinator 가 **모두 끝나기를
기다린 뒤 한 번만** 수행한다.

바깥에서 가져다 쓰는 것들과 그 역할은 이렇다.

| 무엇 | 어디에 쓰나 |
|---|---|
| FastAPI · uvicorn | HTTP 요청을 받는 뼈대와 서버. API 설명서 화면도 여기서 나온다 |
| sqlglot | SQL 을 해석해 규칙에 맞는지 보고 파티션 조건을 찾아낸다 |

문법이 조금씩 다르기 때문이다.

쿼리를 만드는 일은 **제한된 환경**에서 이루어진다. 그리고 만들어진 문장이 **하나인지 검사한다.**
값에 세미콜론을 끼워 넣어 엉뚱한 명령을 덧붙이는 공격을 막기 위해서다.

## 3. 실행·적재 SW 기술 구조

### 3.1 실행·적재 SW 기술 구조 정의

#### 3.1.1 모듈 구조 관점

윗층인 앱 계층은 **조각을 받아 상태를 관리하고 동시에 몇 개까지 돌릴지만** 정한다. 그 아래 백엔드가
**실제로 원본에서 읽고 목적지에 넣는다.**

백엔드는 **인터페이스로 정의돼 있다.** "이런 함수들이 있어야 한다"는 약속만 정해 두었다는 뜻이다.
그래서 실제로 일하는 구현과 테스트용 가짜 구현이 같은 자리에 들어갈 수 있다.

그 밖에 S3 를 다루는 부분, 자기 상태를 보고하는 부분, 조각 기록을 남기는 부분이 각각 따로 있다.

![클래스 — executor 와 적재 백엔드](images/class-executor-backend.svg)

#### 3.1.2 런타임 구성 관점

동시에 돌릴 조각 수는 **표를 정해진 장 수만 발행하는 방식**으로 제한한다. 표가 없으면 기다린다.

목적지 연결은 만들어 둔 것을 돌려 쓴다. 다만 돌려받을 때 **세션을 깨끗이 초기화한다.** 그러지 않으면
앞 조각이 만든 임시 테이블이 남아 다음 조각과 부딪힌다.

데이터베이스를 부르는 일은 끝날 때까지 붙들려 있는 종류라 모두 별도의 실행 흐름으로 넘긴다. 그리고
**읽는 일과 쓰는 일을 겹쳐 실행해** 전체 걸리는 시간을 줄인다. 읽고 나서 쓰는 것이 아니라, 읽으면서
동시에 쓴다.

종료 신호를 받으면 곧바로 죽지 않는다. **돌고 있는 조각이 끝나기를 정해진 시간만큼 기다렸다가**
내려간다.

#### 3.1.3 배포 관점

한 서버에 포트를 달리해 여러 대를 띄울 수 있고, **처리량은 이 수로 늘린다.**

여기서 초보자가 자주 겪는 함정이 있다. **coordinator 의 목록에 없으면 프로세스를 띄워도 일이 가지
않는다.** 띄우기만 하고 목록에 넣지 않으면 아무 일도 일어나지 않으므로, 목록을 먼저 고치고 띄운다.

두 가지 조건이 더 있다. `local_stage` 방식을 쓴다면 executor 를 **목적지 세그먼트와 같은 서버에**
두어야 한다. coordinator 를 여러 대 쓴다면 executor 가 **자기 상태를 공유 저장소에 직접 보고하도록**
켜 준다.

### 3.2 실행·적재 SW 기술 구조 상세설계

#### 3.2.1 구조 개요

조각을 받으면 대기 줄에 넣고 **곧바로 "받았다"고만 응답한다.** 실제 실행은 그 뒤에 시작한다.

차례가 오면 읽기 상태로 올라가 원본에서 묶음 단위로 읽고, 쓰기 상태로 넘어가 목적지에 넣는다. 끝나면
처리한 건수와 단계별로 걸린 시간을 상태에 채워 두고, coordinator 가 물어볼 때 그것을 답한다.

#### 3.2.2 구성 요소

| 구성 요소 | 역할 |
|---|---|
| 앱 계층 | task 접수와 상태머신, 동시 실행 상한, 상태·결과 응답 |
| 백엔드 인터페이스 | exec_mode 별 진입점을 하나의 계약으로 묶는다 |
| 실제 백엔드 | 소스 커서 열기, 스트리밍, 대상 적재와 스테이징 SQL 실행 |
| MockBackend | 대상 접속 정보가 없을 때 뜨는 테스트용 구현 |
| 연결 풀 | 대상 연결 재사용과 반납 시 세션 초기화 |
| 커서 어댑터 | 커서를 주지 않는 소스를 커서처럼 감싼다 |
| 스토리지 클라이언트 | 스테이징 객체 업로드와 삭제 |
| 상태 보고·이력 | 자기 자원 상태 보고와 task 이력 기록 |

#### 3.2.3 구조 상세 설계

**`exec_mode` 라는 필드 하나가 데이터가 지나는 길을 정한다.** 요청의 나머지 모양은 똑같은데 이 값
하나로 경로가 갈린다.

곧장 밀어 넣을지, 임시 테이블을 거칠지, 파일을 만들어 목적지가 당겨 읽게 할지가 달라진다.

![exec_mode 다섯 가지 경로](images/exec-modes.svg)

**데이터는 묶음 단위로 흘려보내고, 걸린 시간을 함께 잰다.** 결과 전체를 메모리에 올리지 않으므로
데이터가 아무리 커도 메모리는 일정하다.

읽는 일과 쓰는 일은 겹쳐 실행하되, 걸린 시간을 **네 갈래로 나눠** 기록한다. 그래서 느릴 때 어디가
문제인지를 짐작이 아니라 값으로 가릴 수 있다.

**원본이 여러 가지여도 읽는 코드는 하나다.** 어댑터가 그 차이를 흡수하기 때문이다.

읽는 코드가 원본에 요구하는 것은 사실 셋뿐이다. "컬럼이 무엇인지 알려 줘", "다음 묶음을 줘", "다
썼으니 닫아 줘". 그래서 데이터베이스가 아닌 사내 API 도 그 세 가지 모양으로 감싸면 읽는 코드는 한
줄도 바뀌지 않는다.

다만 여기에 **반드시 지켜야 할 구분**이 있다. 미리보기용 함수와 이관용 함수는 약속이 다르다.
미리보기는 정해진 줄 수에서 자르지만, **이관은 전부 돌려주는 것이 약속이다.** 이것을 어기면 잘린
데이터가 조용히 들어간다.

**2단계로 넣는 방식에서 executor 는 절반만 한다.** 파일을 만들어 두는 데까지가 executor 의 몫이고,
그 파일을 목적지가 읽게 만드는 일은 coordinator 가 **모두 끝나기를 기다린 뒤에** 한다.

![s3_stage 의 2단계 적재](images/s3-stage-phases.svg)

### 3.3 실행·적재 SW 기술 구조 시스템 공통 모듈

#### 3.3.1 일반 공통 모듈 목록

설정과 로깅, 비밀 가리기, 시각, 자원 계측 모듈은 제어 쪽과 **똑같은 것을 그대로 쓴다.**

여기에 둘이 더해진다. 하나는 조각의 단계별 시각표를 만드는 모듈이고, 다른 하나는 파일을 목적지가
읽게 만드는 SQL 을 조립하는 모듈이다.

뒤엣것은 **순수 함수로 만들어 두었다.** 바깥 상태를 건드리지 않고 값을 넣으면 값이 나오는 함수라는
뜻이다. 그래야 실제 데이터베이스 없이 만들어진 문자열만 비교해 테스트할 수 있다.

#### 3.3.2 솔루션 관련 공통 모듈

원본 접속은 impyla 와 인증 관련 패키지, 목적지 접속은 psycopg, S3 는 boto3 를 쓴다.

셋 다 **실제로 필요한 순간에만 불러온다.** 그래서 쓰지 않는 기능의 패키지가 설치돼 있지 않아도
나머지는 잘 돈다. S3 를 안 쓴다면 boto3 가 없어도 된다는 뜻이다.

## 4. CLI·운영 도구 SW 기술 구조

### 4.1 CLI·운영 도구 SW 기술 구조 정의

#### 4.1.1 모듈 구조 관점

명령마다 시작점이 되는 모듈이 하나씩 있다. 그 아래에 엔진과 셸, 설정 변환, SQL 파일 읽기, 표 출력,
진행 표시가 **공통 부품으로 깔린다.**

대화형 셸은 엔진과 셸로 나뉘어 있다. **엔진만 갈아 끼우면 다른 데이터베이스에서도 같은 셸이 돈다.**

![클래스 — 운영자 CLI 도구](images/class-tools.svg)

#### 4.1.2 런타임 구성 관점

같은 모듈이 **두 얼굴**을 갖는다. 인자를 주면 한 번 실행하고 끝나고, 대화형 옵션을 주면 셸이 열린다.

여기에 더해 **사람이 보고 있는지 아닌지**에 따라서도 행동이 달라진다. 자동 실행처럼 사람이 없는
상황이면 이렇게 바뀐다.

- 입력을 기다리는 프롬프트와 명령 기록을 끈다 — 아무도 답하지 않으면 영영 멈추기 때문이다
- 삭제는 확인 옵션 없이는 아예 거부한다
- 진행 표시를 같은 줄에 덮어쓰지 않고 새 줄에 쓰되, 간격을 크게 벌린다 — 로그가 진행 표시로 뒤덮이지
않게 하려는 것이다

#### 4.1.3 배포 관점

서비스와 **같은 디렉터리에 놓이고 같은 설정을 읽는다.**

실행 스크립트가 자기 위치에서 최상위 디렉터리를 찾아 경로를 잡으므로, **어느 디렉터리에서 불러도
같은 코드와 같은 설정이 쓰인다.** 파이썬은 설치된 실행 환경을 먼저 찾고, 환경변수로 직접 지정할 수도
있다.

### 4.2 CLI·운영 도구 SW 기술 구조 상세설계

#### 4.2.1 구조 개요

사람이 직접 하는 일은 셋이다. 이관 결과를 목적지에서 바로 확인하는 일, 원본에서 표본을 뽑아 보는 일,
중간 파일로 남은 것을 정리하는 일이다.

**서비스가 못 하는 일이라서 도구를 둔 것이 아니다.** 사람이 지금 당장 확인해야 하는 일을 맡는
자리다.

#### 4.2.2 구성 요소

| 도구 | 하는 일 | 의존 |
|---|---|---|
| 대상 SQL 셸 | 대상에 붙어 조회·DDL·DML 실행 | psycopg |
| 소스 SQL 셸 | 소스에 붙어 조회 | impyla · SASL |
| 오브젝트 도구 | 목록·업로드·다운로드·복사·이동·삭제·내용 확인 | boto3 |
| 설정 편집기 | 설정 항목을 스키마에서 읽어 편집하고 정합을 검사 | 표준 라이브러리 |
| 상태 모니터 | 같은 API 를 폴링해 터미널에 상태를 그린다 | 표준 라이브러리 |

#### 4.2.3 구조 상세 설계

**설정 파일을 새로 만들지 않는다.** 도구는 서비스의 설정을 읽어 자기가 기대하는 모양으로 바꿔 쓸
뿐이다. 접속 정보가 한 줄로 적힌 항목은 변환기가 풀어 준다.

**왜 그럴까.** 같은 값을 두 곳에 적어 두면 반드시 한쪽만 고치는 날이 오기 때문이다. 그러면 서비스는
새 데이터베이스를 보고 도구는 옛 데이터베이스를 보는 사고가 난다.

**비밀번호를 명령행 인자로 받지 않는다.** 명령행에 적으면 같은 서버의 다른 사용자가 실행 중인
프로세스 목록을 보는 것만으로 그 값을 읽을 수 있기 때문이다. 설정 파일, 환경변수, 직접 입력 순으로만
찾는다.

**끝날 때 남기는 숫자로 원인을 가른다.** 성공, 대상이 없거나 취소됨, 인자를 잘못 줌, 패키지가 없음,
접속 실패, 실행 실패나 권한 없음을 서로 다른 숫자로 구분한다.

이 구분이 있으면 자동 실행 스크립트가 **다시 시도할 가치가 있는지 스스로 판단할 수 있다.** 접속
실패는 다시 해 볼 만하지만 인자를 잘못 준 것은 몇 번을 해도 같기 때문이다.

**보고와 데이터를 다른 통로로 내보낸다.** 걸린 시간과 진행 상황은 오류 통로로, 조회 결과는 출력
통로로 나간다. 그래서 결과를 다른 명령으로 넘겨도 진행 표시가 섞이지 않는다.

### 4.3 CLI·운영 도구 SW 기술 구조 시스템 공통 모듈

#### 4.3.1 일반 공통 모듈 목록

설정 변환, SQL 파일 읽기, 표 출력, 진행 표시와 시간 측정, 그리고 **글자 폭 계산**을 공통으로 쓴다.

마지막 것을 따로 설명해 둔다. **한글 한 글자는 터미널에서 두 칸을 차지한다.** 그래서 글자 수로 잘라
화면에 쓰면 실제 폭이 두 배까지 밀린다. 그렇게 넘긴 문자열은 화면 맨 아랫줄에서 **터미널 화면을
통째로 죽인다.** 그래서 화면에 쓰기 전에는 반드시 이 계산을 거치게 되어 있다.

#### 4.3.2 솔루션 관련 공통 모듈

드라이버는 서비스와 **같은 것을 쓴다.** 목적지는 psycopg, 원본은 impyla, S3 는 boto3 다. 셋 다
executor 쪽 의존성에 이미 들어 있으므로 **도구를 위해 따로 설치할 것이 없다.**

# IV. SW 아키텍처의 적용

## 1. 이관 서비스 SW 아키텍처

### 1.1 Application 관점

#### 1.1.1 API·제어 SW 기술 구조 관점

앞에서 정의한 구조가 coordinator 에 **그대로 적용돼 있다.** 문서와 코드가 따로 놀지 않는다는 뜻이다.

요청을 받는 함수는 **판단만 하고 실행은 넘긴다.** 검사와 분할은 바깥 상태를 건드리지 않는 순수
함수로 떨어져 있어 실제 데이터베이스 없이 테스트된다.

전체 흐름은 부모 클래스가 모두 쥐고 있고 자식은 **"어떻게 실행하는가" 한 가지만** 구현한다. 그래서
다른 서버에 보내 실행하든 자기 안에서 실행하든 **같은 상태 변화와 같은 집계 규칙**을 따른다.

![클래스 — coordinator 요청 처리](images/class-coordinator.svg)

나중에 늘려야 할 자리도 구조 안에 마련해 두었다. 쿼리는 템플릿으로 코드 바깥에 두고, 템플릿에서 쓸
함수는 등록해서 더하며, 저장소는 인터페이스 하나에 구현이 셋이라 **코드를 고치지 않고 설정만으로**
한 대 구성과 여러 대 구성을 오갈 수 있다.

#### 1.1.2 실행·적재 SW 기술 구조 관점

executor 는 상태 관리와 동시 실행 제한만 직접 들고, **나머지는 모두 백엔드 인터페이스 뒤에 있다.**

이 구조가 세 가지를 가능하게 한다. 목적지 접속 정보가 없으면 가짜 구현으로 떠서 **전 구간을
테스트**할 수 있고, 원본이 데이터베이스가 아니어도 어댑터가 그 자리를 메우며, **옮기는 방식이
늘어나도 윗층은 함수 하나를 더 부를 뿐**이다.

### 1.2 배포 관점

#### 1.2.1 API·제어 SW 기술 구조 관점

coordinator 는 디렉터리 하나에 일꾼 하나로 뜬다.

**켜고 끄는 순서가 정해져 있다.** 끌 때는 coordinator 부터, 켤 때는 executor 부터다. 받아 줄 곳이
없는 상태에서 요청을 받지 않기 위해서다.

설정은 기동할 때 굳으므로 값을 바꾸면 다시 띄워야 한다. 그리고 기동 로그에 찍히는 안내로 **어떤 설정
파일을 읽었는지** 확인한다.

여러 대를 띄우려면 상태를 공유 저장소로 빼내고 각자 살아 있음을 남기게 켠다. 이때 **받아 줄지
판단하는 한도가 서버마다 따로 적용된다**는 점을 감안해 총량을 나눠 잡는다.

#### 1.2.2 실행·적재 SW 기술 구조 관점

executor 를 **늘리고 줄이는 순서**가 정해져 있다.

늘릴 때는 목록에 주소를 먼저 넣고, 새 서버를 띄운 뒤, coordinator 를 다시 띄워 목록을 읽게 한다.

줄일 때는 그 반대다. 목록에서 빼고 coordinator 를 다시 띄워 **새 일이 가지 않게 한 뒤**, 돌던 조각이
끝나기를 기다렸다 내린다. 순서를 지키지 않으면 실행 중인 조각이 통째로 실패한다.

늘린 뒤에는 **함께 움직여야 하는 값**이 있다. 한꺼번에 내보낼 조각 수의 상한이 늘어난 전체 용량보다
작지 않은지, 목적지가 허용하는 접속 수를 넘지 않는지 확인한다. `local_stage` 방식이라면 새 서버도
세그먼트 위에 있어야 하고 호스트 이름 설정이 정확히 맞아야 한다.

### 1.3 구현 관점

#### 1.3.1 API·제어 SW 기술 구조 구현 관점

코드는 `src/coordinator/` 아래에 있고 **모듈 이름이 곧 역할이다.** 앱과 모델, 파서와 splitter,
템플릿, dispatcher, 저장소, 이력, 감시, executor 고르기와 예약, 화면이 각각 파일 하나씩이다.

**늘릴 수 있는 자리는 셋이다.** 템플릿 디렉터리에 새 시나리오를 더하는 것, 템플릿에서 쓸 함수 모듈을
설정으로 추가하는 것, 저장소 구현을 설정으로 바꾸는 것이다. 셋 다 코드를 고치지 않는다.

테스트는 실제 데이터베이스 없이 돈다. 가짜 백엔드와 가짜 실행기로 검사·분할·수용 판단·상태
변화·화면·로그까지 덮는다. 터미널 화면은 **화면 밖에 쓰면 실패하는 가짜 터미널**로 여러 크기에서
훑어 확인한다.

#### 1.3.2 실행·적재 SW 기술 구조 구현 관점

코드는 `src/executor/` 아래에 있다. 앱과 모델, 백엔드, S3 클라이언트, 상태 보고, 이력이 파일
하나씩이고 **백엔드가 가장 크다.**

늘릴 수 있는 자리는 원본 쪽에 있다. 데이터베이스가 아닌 원본을 쓰려면 함수 하나를 설정으로 지정하면
되고, 그 함수가 돌려주는 형태는 여러 가지를 받아 준다.

**반드시 지켜야 할 구현 규칙이 하나 있다.** 미리보기 함수와 이관 함수는 이름이 비슷해도 약속이
다르다. 앞은 정해진 줄 수에서 자르고 **뒤는 전부 돌려주는 것이 약속이다.** 이 둘을 섞으면 잘린
데이터가 조용히 들어간다. 그래서 어느 쪽인지 판정하는 코드는 한 곳에만 두고, 설정이 없으면 다른
것으로 대신하지 않고 **명확히 실패시킨다.**

## 2. 운영 도구 SW 아키텍처

### 2.1 Application 관점

#### 2.1.1 CLI·운영 도구 SW 기술 구조 관점

도구 셋은 앞에서 정의한 구조를 그대로 따른다. 명령마다 시작점이 있고 공통 부품을 함께 쓰며, 대화형
셸은 엔진과 셸로 나뉘어 **원본용과 목적지용이 같은 셸을 쓴다.** 설정은 서비스 것을 읽어 모양만 바꿔
주므로 **접속 정보가 한 곳에만 있다.**

터미널에 화면을 그리는 두 도구, 곧 설정 편집기와 상태 감시기도 같은 계열이다. 계산 부분을 화면
그리기와 떼어 두어 테스트할 수 있게 했고, 외부 인터넷이 막힌 환경을 고려해 **파이썬이 기본으로 주는
것만 쓴다.**

#### 2.1.2 배치 실행 관점

**자동 실행에 걸어 두는 것을 전제로 만들었다.** 그래서 세 가지를 미리 처리해 두었다.

어느 디렉터리에서 실행하든 **같은 설정을 읽는다.** 출력 인코딩과 버퍼링을 미리 잡아 두어 **한글을
출력하다 죽거나 로그가 뒤늦게 몰려 나오지 않는다.** 사람이 보고 있지 않으면 입력을 기다리는
프롬프트를 띄우지 않으므로 **영영 멈추는 일이 없다.**

실패했는지는 끝날 때 남기는 숫자로 판별한다. 환경이나 접속 문제는 다시 해도 소용이 없고, 실행 실패나
권한 문제는 사람이 봐야 하며, 대상이 없어 끝난 경우는 대개 정상이다. 이 구분이 있어 **자동 실행
스크립트가 스스로 판단할 수 있다.**

```bash
#!/bin/bash
set -euo pipefail
export IMPALA_PASSWORD="$(cat /etc/etl/impala.pw)"
D=/data1/distributed-query-executor
PYTHONPATH=$D/src $D/.venv/bin/python -m tools.impala_query -f daily_orders.sql \
    -V "dt=$(date -d yesterday +%Y-%m-%d)" -o /data/orders.csv.gz --gzip
$D/bin/s3-ops upload /data/orders.csv.gz s3://dw-stage/orders/ 
```

## 3. 연계 아키텍처

### 3.1 연계 아키텍처 정의

이 시스템은 **스스로 데이터를 만들지 않는다.** 다른 시스템에서 읽어 다른 시스템에 넣는 것이 존재
이유다. 그러므로 **바깥과 이어지는 일은 부가 기능이 아니라 본체다.**

이어지는 성격은 셋으로 나뉜다.

- **데이터 연계** — 데이터를 읽고 쓴다
- **상태 연계** — 상태와 기록을 남긴다
- **제어 연계** — 일을 맡기고 결과를 받는다

### 3.2 연계 아키텍처 구성

#### 3.2.1 연계 아키텍처 개요

무엇과 어느 방향으로 이어지는지를 한 장으로 정리하면 이렇다. 세 가지만 기억하면 그림이 읽힌다.
**데이터는 coordinator 를 지나지 않고, 원본에는 executor 만 접속하며, 파일을 목적지가 읽게 만드는
SQL 은 coordinator 가 중앙에서 실행한다.**

![연계 논리 모델](images/integration-model.svg)

#### 3.2.2 연계 범위

| 연계 대상 | 주고받는 것 | 방향 | 접속 주체 |
|---|---|---|---|
| 소스 엔진 | 분할된 SELECT 와 그 결과 행 | 읽기 | executor |
| 소스 커스텀 API | 같은 SELECT 를 함수 호출로 위임하고 결과를 받음 | 읽기 | executor |
| 적재 대상 | COPY 스트림, staging·target INSERT, 외부테이블 DDL | 쓰기 | executor · coordinator |
| 스테이징 매체 | CSV 객체와 파일, 적재 후 정리 | 쓰기·삭제 | executor · coordinator |
| 메타 저장소 | job 상태, 실행 이력, executor 상태, 예약, 메트릭 | 읽기·쓰기 | coordinator · executor |
| 요청 주체 | job 제출과 상태·결과 조회 | 수신 | coordinator |

#### 3.2.3 연계 논리 모델 다이어그램

위 그림이 논리 모델을 겸한다.

읽을 때 **상자가 시스템이 아니라 역할**이라는 점을 기억하면 쉽다. 원본이 Impala 든 사내 API 든 "읽는
역할"은 하나다. 목적지와 외부테이블도 서로 다른 시스템이 아니라 **같은 데이터베이스에 접근하는 두
가지 방식**이다.

### 3.3 연계 기술구조

#### 3.3.1 연계 유형(패턴)

| 유형 | 어디에 쓰나 | 특징 |
|---|---|---|
| 드라이버 직접 접속 | 소스 읽기, 대상 적재, 메타 저장소 | 커넥션을 열어 SQL 을 실행한다. 가장 단순하고 계측이 쉽다 |
| 함수 위임 | 커서를 주지 않는 사내 API | 설정으로 지정한 함수를 부르고 결과를 커서처럼 감싼다 |
| HTTP 호출 | coordinator 와 executor 사이 | task 지시와 상태 조회. 실패하면 재시도 후 다른 노드로 넘긴다 |
| 외부테이블 당겨 읽기 | 2단계 적재의 Phase 2 | 파일을 만들어 두고 대상 세그먼트가 병렬로 읽는다 |
| 오브젝트 스토리지 경유 | 세그먼트와 같은 호스트에 둘 수 없을 때 | 위치에 무관해 배치 제약이 없다 |

#### 3.3.2 개발환경

**이어질 상대가 없어도 개발과 테스트가 된다.**

목적지 접속 정보가 비면 아무것도 읽고 쓰지 않는 가짜 구현이 뜬다. 파일을 읽게 만드는 SQL 조립은 순수
함수라 만들어진 문자열만 비교하면 된다. HTTP 로 이어지는 부분은 가짜 실행기로 대신한다.

실제 연결을 처음 붙일 때는 **작은 작업 하나를 끝까지 돌려 보는 것**이 가장 확실한 확인이다. 설정을
아무리 들여다봐도 실제로 한 번 돌려 보는 것만 못하다.

#### 3.3.3 연계 공통 기능

이어질 때마다 반복되는 것들을 공통으로 뺐다.

**접속 설정** — 한 파일에서 읽어 서비스와 도구가 함께 쓴다.

**인증** — 원본 쪽에만 걸리며 인증서 경로까지 설정에 있다.

**실행 SQL 기록** — 어느 데이터베이스에 어떤 문장을 던졌는지를 **항상** 남긴다. 사고가 났을 때 가장
먼저 보는 근거다.

**오류 처리와 재시도** — 성격에 따라 다르게 정해 두었다. HTTP 는 몇 번 다시 걸어 본 뒤 다른 서버로
넘긴다. 데이터베이스는 실패를 그대로 올려 작업 상태에 집계한다. S3 업로드는 권한 때문에 **큰 파일만
실패하는** 특이한 경우를 따로 다룬다.
