# 클래스 다이어그램

이 문서는 **코드를 처음 여는 사람**이 어느 파일에 무엇이 있는지 그림으로 먼저 잡을 수 있도록 만든
것이다.

클래스 다이어그램이라는 말이 낯설 수 있다. 프로그램을 이루는 부품 하나하나를 상자로 그리고, 그
부품들이 서로 어떻게 이어지는지를 선으로 이은 그림이다. 코드를 한 줄씩 읽기 전에 전체 지도를 먼저
보는 셈이다.

기능 단위로 일곱 장을 그렸다. 각 장에는 그 기능에 실제로 관여하는 부품만 담았다. 모든 것을 한 장에
몰아넣으면 선이 얽혀 아무것도 읽히지 않으므로, 한 장에서 한 가지 일만 좇을 수 있게 나눴다.

## 그림 읽는 법

규칙은 UML 이라는 표준을 따르되 느슨하게 썼다. 아래 다섯 가지만 알면 읽을 수 있다.

| 그림에서 보이는 것 | 뜻 |
|---|---|
| 상자 맨 위 칸 | 부품의 이름 |
| 그 아래 칸 | 그 부품이 들고 있는 값(속성) |
| 그 아래 칸 | 그 부품이 할 수 있는 일(메서드) |
| 이름 위의 «…» | 그것이 보통 클래스가 아니라 모듈·프로토콜·열거형·파일이라는 표시 |
| 속 빈 삼각형 / 마름모 / 실선 화살표 / 점선 화살표 | 차례로 상속하거나 구현한다 / 소유한다 / 참조한다 / 호출하거나 의존한다 |

지면에 다 담을 수 없는 메서드는 생략했다. 그러므로 **정확한 이름과 인자는 언제나 코드가
기준이다.** 이 그림은 길잡이이지 명세가 아니다.

그림은 `images/` 아래에 SVG 와 PNG 를 함께 둔다. 문서에는 확대해도 글자가 뭉개지지 않는 SVG 를 넣고,
발표 자료처럼 SVG 를 못 읽는 곳에는 같은 이름의 PNG 를 쓴다. 둘은 같은 원본에서 나오므로 그림을 고칠
때는 SVG 를 고치고 PNG 를 다시 뽑아 함께 갱신한다.

## coordinator 요청 처리

이관 요청 하나가 들어와 실행으로 넘어가기까지를 담았다.

요청은 먼저 `CreateJobRequest` 라는 상자에 담겨 들어온다. 그다음 parser 가 "이 SQL 이 규칙에
맞는가"를 검사하고, splitter 가 그 SQL 을 여러 조각으로 쪼갠다. 그리고 `JobAdmission` 이 "지금 이걸
받아도 되는가"를 판단한 뒤에야 비로소 `Job` 이 만들어진다. 쿼리를 서버에 미리 등록해 두는 템플릿을
쓰는 요청이면, 그 앞에 `TemplateEngine` 이 SQL 을 만들어 채워 준다.

실행을 맡는 부품은 **상속**으로 갈린다. 상속이란 공통된 부분을 부모 상자에 두고 다른 부분만 자식
상자에서 채우는 방식이다. 여기서는 `_DispatcherBase` 라는 부모가 "기다렸다가 실행하고 결과를
모은다"는 전체 흐름을 모두 쥐고 있고, 자식은 `_execute()` 라는 함수 하나만 채운다. 다른 서버에 일을
보내는 것이 `HttpDispatcher`, coordinator 안에서 직접 도는 것이 `LocalDispatcher` 다.

![클래스 — coordinator 요청 처리](images/class-coordinator.svg)

`Job` 과 `Task` 는 상태를 담아 두는 상자이면서, 화면과 API 응답에 쓸 형태까지 스스로 만들어 준다.
`to_record()` 와 `from_record()` 라는 함수가 있는 이유는 이 둘을 데이터베이스에 통째로 넣었다가
그대로 꺼내 쓰기 때문이다.

## 작업 저장소와 이력

작업 상태를 어디에 둘 것인가는 **규약 하나에 구현이 셋**인 구조로 풀었다. 규약이란 "이런 함수들을
갖고 있어야 한다"는 약속이고, 그 약속만 지키면 속은 무엇이든 될 수 있다.

| 구현 | 언제 쓰나 |
|---|---|
| `InMemoryJobStore` | coordinator 한 대. 메모리에만 두므로 재시작하면 사라진다 |
| `FileJobStore` | 한 대지만 재시작 후에도 상태를 잃고 싶지 않을 때 |
| `SqlJobStore` | coordinator 여러 대. 공유 데이터베이스에 둔다 |

셋 중 무엇을 쓸지는 `build_job_store()` 가 설정값 하나를 보고 정한다. 그래서 일을 배분하는 쪽은 지금
어느 구현이 쓰이는지 알 필요가 없다.

![클래스 — 작업 저장소와 이력](images/class-job-store.svg)

이력은 저장소와 별개다. 작업 단위 기록은 coordinator 가 쓰고, **조각 단위 기록은 executor 가 직접
쓴다.** 그래서 executor 가 있는 서버에서도 그 데이터베이스에 닿을 수 있어야 한다. 이 점을 놓치면
이력만 비게 된다.

살아 있음을 알리는 신호와 자리 예약은 coordinator 를 여러 대 띄울 때만 쓰인다. 서로가 살아 있는지
확인하고 일감을 나누기 위한 장치다. 이 표들은 **앱이 만들어 주지 않으므로** 운영자가 미리 만들어
두어야 한다.

## 쿼리 템플릿 엔진

클라이언트가 SQL 전문을 보내는 대신, 서버에 미리 등록해 둔 쿼리의 이름과 값만 보내는 방식이 있다. 그
일을 하는 것이 템플릿 엔진이다.

`manifest.yml` 이라는 설명 파일과 `*.sql.j2` 라는 쿼리 조각들을 읽어, 값을 채워 실제 SQL 을 만들어
낸다. 만들어진 결과는 원래 요청에 그대로 끼워 넣어지므로, **그 뒤의 처리 경로는 SQL 을 직접 보냈을
때와 완전히 같다.** 앞단만 다르고 뒷단은 하나라는 뜻이다.

![클래스 — 쿼리 템플릿 엔진](images/class-template.svg)

쿼리를 만들 때 쓸 수 있는 함수도 등록해 둘 수 있다. 기본으로 문자열을 안전하게 감싸 주는 것, 목록을
만들어 주는 것, 날짜 구간을 펼쳐 주는 것 등을 제공한다.

안전장치가 둘 있다. 하나는 템플릿을 **제한된 환경**에서만 실행한다는 것이고, 다른 하나는 만들어진
SQL 이 **문장 하나인지 검사**한다는 것이다. 뒤엣것은 값에 세미콜론을 넣어 엉뚱한 명령을 덧붙이는
공격을 막기 위한 것이다.

## executor 와 적재 백엔드

executor 는 작업 조각의 상태를 관리하고 동시에 몇 개까지 돌릴지만 정한다. **실제로 읽고 쓰는 일은
`Backend` 라는 규약 뒤에 감춰져 있다.**

실제로 일하는 구현이 `ImpalaToGreenplumBackend` 이고, 목적지 접속 정보가 비어 있으면 **아무것도 하지
않는 `MockBackend`** 로 뜬다. 뒤엣것은 개발과 테스트를 실제 데이터베이스 없이 하기 위한 것이다.

여기서 실무에서 자주 겪는 함정이 하나 있다. **작업이 성공했다는데 목적지에 데이터가 없다면 이
갈림길을 가장 먼저 의심한다.** 접속 정보를 빠뜨려 아무것도 하지 않는 쪽으로 떴을 가능성이 크다.
기동할 때 경고 로그가 남으므로 그것부터 확인한다.

![클래스 — executor 와 적재 백엔드](images/class-executor-backend.svg)

이 그림에서 눈여겨볼 부품이 둘 있다.

**어댑터** — 데이터를 읽는 코드가 원본에 요구하는 것은 사실 세 가지뿐이다. "컬럼이 무엇인지 알려
줘", "다음 묶음을 줘", "다 썼으니 닫아 줘". 그래서 데이터베이스가 아닌 사내 API 가 원본이어도,
`_FunctionConnection` 과 `_FunctionCursor` 로 그 세 가지 모양만 갖춰 감싸면 읽는 코드는 한 줄도
바뀌지 않는다.

**연결 풀** — 데이터베이스 연결은 만들 때마다 비용이 든다. 그래서 `_GreenplumPool` 이 만들어 둔
연결을 돌려 쓴다. 다만 돌려받을 때 **세션을 깨끗이 초기화**하는데, 그러지 않으면 앞 작업이 만들어 둔
임시 테이블이 남아 다음 작업과 부딪히기 때문이다.

## 헬스 모니터링과 여러 coordinator

`HealthMonitor` 는 주기적으로 모든 executor 를 찾아가 "살아 있는가, 얼마나 바쁜가"를 물어 모아 둔다.
그리고 `ExecutorSelector` 가 다음 일감을 어디로 보낼지 정할 때 그 값을 근거로 쓴다.

그래서 **모니터링을 끄면 "가장 한가한 곳으로 보내기" 같은 방식이 근거를 잃는다.** 끄려면 배분 방식도
함께 단순한 것으로 바꿔야 한다.

![클래스 — 헬스 모니터링과 여러 coordinator](images/class-ha-monitor.svg)

coordinator 를 여러 대 띄우면 서로가 살아 있는지 알 방법이 필요하다. 각자 `CoordinatorHeartbeat` 로
"나 살아 있다"를 주기적으로 남기고, 신호가 끊긴 coordinator 가 쥐고 있던 작업은
`reconcile_orphaned_jobs()` 가 대신 거둬 정리한다.

일감을 보내는 동안 자리를 미리 잡아 두는 **예약**도 있다. 여러 coordinator 가 같은 순간에 같은
executor 를 고르는 쏠림을 줄이기 위한 장치다.

## 공용 core 모듈

coordinator 와 executor 가 함께 쓰는 부품들이다.

**설정** — `config.properties` 에 적은 값이 `config.yml` 의 빈자리를 채워 `Settings` 하나로 굳는다.
여기서 놓치기 쉬운 함정이 있다. `config.yml` 에 그 빈자리가 없으면 properties 에 값을 적어도
**조용히 무시된다.** 새 버전으로 올릴 때 `config.yml` 을 반드시 교체해야 하는 이유가 이것이다.

![클래스 — 공용 core 모듈](images/class-core.svg)

**로깅** — 세 갈래로 나뉜다. 하나는 로그 파일을 날짜별로 나누고 모든 줄에 작업 번호를 붙이는 것,
둘은 실행한 SQL 을 어느 데이터베이스에 어느 단계에서 던졌는지와 함께 남기는 것, 셋은 HTTP 요청과
응답을 상세 모드에서만 남기는 것이다.

여기에 데이터를 미리 몇 줄 훑어보는 기능과, 임시 파일을 목적지가 읽게 만드는 SQL 을 조립하는 기능이
더해진다. 이 부품들을 coordinator 와 executor 가 그대로 나눠 쓴다.

## 운영자 CLI 도구

서비스와 별개로, 사람이 터미널에서 직접 두드리는 도구 셋이다.

대화형 셸은 두 부품으로 나뉜다. `Engine` 이 "어느 데이터베이스에 어떻게 붙고 목록을 어떻게
조회하는가"를 알고, `Shell` 이 "입력을 받아 실행하고 결과를 보여 주고 자동완성과 페이저를
제공한다"를 맡는다. 이렇게 갈라 둔 덕에 **Impala 용과 Greenplum 용이 같은 셸을 쓴다.** 엔진만 갈아
끼우면 된다.

![클래스 — 운영자 CLI 도구](images/class-tools.svg)

여기서 가장 중요한 부품은 `appconfig` 다. 이 도구들은 **자기 설정 파일을 따로 두지 않는다.**
서비스가 쓰는 `config.properties` 를 읽어 도구가 기대하는 모양으로 바꿔 줄 뿐이다. 접속 정보를 두
곳에 적어 두면 한쪽만 고쳐서 어긋나는 사고가 나기 때문이다.

Greenplum 만 설정 형태가 달라서, `parse_dsn()` 이 한 줄로 적힌 접속 문자열을 주소와 포트, 사용자로
풀어 준다.

# 부록 — 이웃 저장소 whpg-to-whpg

여기까지가 이 저장소의 그림이다. 아래는 같은 계열의 이관 도구인
[DataDynamics/whpg-to-whpg](https://github.com/DataDynamics/whpg-to-whpg) 를 같은 방식으로 그린
것이다.

이 저장소가 Impala 에서 Greenplum 으로 옮기는 **서비스**라면, 그쪽은 WarehousePG 테이블 하나를 다른
WarehousePG 로 복사하는 **명령행 도구**다. 함께 쓰는 일이 잦고 설계에서 겹치는 대목이 많아 한 문서에
두었다.

성격이 다르다는 점은 먼저 알아 두는 편이 좋다. 이쪽은 coordinator 와 executor 가 늘 떠 있고 요청이
HTTP 로 들어온다. 그쪽은 **명령 한 번이 곧 작업 하나**라 상태를 프로세스 밖에 둘 필요가 없다. 그래서
요청을 받아 줄지 판단하는 층도, 일감을 나눠 주는 층도, 이력을 남기는 층도 없다.

## whpg-to-whpg — 복사 파이프라인

복사 한 번에 대한 모든 결정은 `CopyPlan` 하나에 모인다. 명령행에 적은 것과 설정 파일에 있는 것,
그리고 양쪽 데이터베이스에서 조회한 정보를 합쳐 이 상자를 만들고 나면, **어떤 컬럼을 어떤 순서로
어떤 형식으로 옮길지가 확정된다.** 그 뒤의 실행 코드는 이 계획만 보고 움직인다.

![클래스 — whpg-to-whpg 복사 파이프라인](images/class-whpg-copy.svg)

이 설계의 핵심은 `copy_local` 과 `copy_s3` 가 **같은 이름의 함수 세
개**(`unload`·`load`·`cleanup`)를 갖는다는 점이다. 부르는 쪽은 모듈만 골라 잡고 그 뒤로는 같은
순서로 부른다. 그래서 모드를 바꿔도 검증과 정리, 보고가 그대로 돌아간다. 이 저장소가 요청 필드
하나(`exec_mode`)로 처리 경로를 고르는 것과 같은 생각이다.

`RecordWriter` 는 local 모드에만 있는 부품이다. 데이터베이스가 흘려보내는 바이트를 받아 파일 여러
개로 나누는 일을 한다. 여기서 조심할 것이 있는데, **아무 데서나 자르면 안 된다.** 데이터 안에
줄바꿈이 들어 있을 수 있어서, 따옴표 안의 줄바꿈에서 자르면 한 줄이 두 파일로 쪼개진다. 그래서
따옴표 밖의 줄바꿈만 경계로 삼는다.

`CopyFormat` 은 형식에 관한 약속을 한 곳에 모은다. 같은 값이 두 자리에 서로 다른 문법으로 들어가야
하기 때문에, 값은 한 번만 정하고 표현만 두 벌로 만들어 준다.

## whpg-to-whpg — 접속과 도구

이 도구의 특징은 **접속 설정이 두 벌 필요하다**는 점이다. 원본과 목적지가 둘 다 데이터베이스이기
때문이다. `ConnectionInfo` 가 그 한 벌을 담고, `whpg` 모듈이 명령행과 설정 파일에서 값을 모아
만든다.

![클래스 — whpg-to-whpg 접속과 도구](images/class-whpg-tools.svg)

나머지는 이 저장소의 운영자 도구와 같은 뿌리다. 대화형 셸을 `Engine` 과 `Shell` 로 나눈 구조, 설정을
한 곳에서 읽어 바꿔 주는 `appconfig`, 표를 출력하고 CSV 를 쓰는 `table`, S3 객체를 다루는
`s3_ops` 가 모두 그렇다. 비밀번호를 명령행 인자로 받지 않는 규칙도 그대로다.
